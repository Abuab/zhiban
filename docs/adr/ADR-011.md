## 一、背景

UI 重构要求把「配对数据删除」显性化，并让数据控制权在界面上可见（归口到 ADR-010 的「隐私与安全检查」页区块④）。

现状核实（均为实测，非推测）：

| # | 事实 | 出处 |
|---|---|---|
| 1 | 邀请域**只有 `cancel`**，语义是「取消邀请」：`UPDATE invite SET status='cancelled', cancelled_at=now()`，**不删任何数据** | `invite.service.ts` L267-282 |
| 2 | 过期任务只把 `status` 置 `expired`，**不做物理删除** | `invite-expire.processor.ts` L37-69 |
| 3 | `docs/schema.sql` **全文无 `FOREIGN KEY ... REFERENCES`、无 `ON DELETE CASCADE`** | 仅 L14 / L606 两处 `SET FOREIGN_KEY_CHECKS`，关联均为应用层弱关联 |
| 4 | 隐私政策已向用户承诺「注销后我们将**物理删除**你的答题数据与报告，不做保留」 | `docs/privacy-policy.md` 第 70 行 |
| 5 | 被邀请方**没有退出通道**：同意后若不愿自己的答案继续留在对方手里，只能等 30 天过期，而过期也**不删数据** | 事实 1 + 2 推导 |

因此：**「取消」不能承担「删除」的语义**（用户以为删了，数据其实还在，与隐私承诺不符）；而**删除又完全没有实现**。

---

## 二、决策 1：新增「删除本次配对数据」，与 `cancel` 严格区分

| 维度 | 取消邀请（既有 `cancel`） | **删除本次配对数据（本次新增）** |
|---|---|---|
| 入口 | 发起方 · 等待页「取消邀请」 | **任一方** · 配对详情页 / 隐私与安全检查页 |
| 数据动作 | 仅改 `invite.status = cancelled` | **物理删除**配对及其全部产物 |
| 可否恢复 | 不可（但**数据仍在**） | 不可（**数据已删**） |
| 对方侧表现 | 仍可看到「已取消」这条记录 | 记录消失，旧链接与旧页面统一 404 |
| 是否改变产品语义 | 是（本次配对作废） | 是（本次配对**不留痕**） |

**保留 `cancel` 不删除数据是对的**：取消后仍要支撑「换人重邀 1 次」（C7）与状态机可追溯；把 `cancel` 改成真删会打断 `replaced_from_invite_id` 的换人链。

## 三、决策 2：**任一方**均可发起删除（含被邀请方）

### 选项
| 选项 | 说明 |
|---|---|
| A. **任一方可删** | 发起方与被邀请方都有删除权；删除后双方同时失效 |
| B. 仅发起方可删 | 与「L1 完整版只归发起方」的归属一致 |
| C. 任一方可删但需对方同意 | 需消息通道，P1 无（且会形成否决权僵局） |

### 决定
**采用 A。**

### 理由
- 知情同意（R8）若只给「同意」不给「撤回」，就是单向的。被邀请方把自己的答案交给了这次配对，**必须有一个出口**收回，否则与 P3「双人数据仅双方可见、可随时注销清空」相悖（背景事实 5）。
- 数据主体是**双方**：报告的原始素材是两个人的答案，任一方都对自己的那一半享有处置权。
- 被邀请方的删除后果与发起方一致（双方同时失效）——因为产物（对比报告、纪念卡）是**共有物**，不存在「只删自己那一半、保留报告」的中间态（保留报告即保留了对方的答案）。

### 代价与边界
- 发起方在 `report_unlocked` 之后仍可被对方一键删除全部报告 → **接受**：数据控制权优先于报告留存；`GET /invites/:code/report` 返回 404。
- 被邀请方「只想撤回自己答案、不想毁掉对方报告」的诉求 **P1 不满足**，记为遗留项（见第九节）。

## 四、决策 3：删除范围 = 按 `invite_id` 显式级联（无外键，必须逐表删）

### 删除（物理删除）
| 表 | 删除条件 | 说明 |
|---|---|---|
| `invite` | `id = :id` | 主体行；**先删它作为「抢删除权」的原子动作**，见决策 4 |
| `answer_sheet` | `invite_id = :id` | 双人答题卷（`scene = 'invite'`） |
| `answer_snapshot` | `invite_id = :id` | 双方答案快照（B8） |
| `report` | `invite_id = :id` | 对比报告本体（含 `dimension_scores_json` / `diffs_json` / `flagged_items_json` / `consensus_json`） |
| `exclusive_card` | `invite_id = :id` | AI 专属卡生成的缓存内容（`invite_id = 0` 的单人行**不受影响**，ADR-008 决策 5） |

### 不删除（留痕，且不含任何作答内容）
| 表 | 处理 | 理由 |
|---|---|---|
| `audit_log` | 保留，**追加一条删除留痕**（谁、何时、删了哪条 `invite_id`） | 删除动作本身需可审计（涉隐私操作的追溯） |
| `visibility_log` | 保留（`report_id` 变为悬空弱关联） | 只含「谁在何时看过报告」，与隐私政策第一章声明的「设备与访问日志」同性质 |
| `consent_log`（ADR-012） | **保留** | 合规举证：证明「同意」与「拒绝同意」确实发生过 |
| `user` | 保留双方账号 | 删除的是**这次配对**，不是账号；单人测评卷（`scene IN ('single','p16')`）不受影响 |

### 关键约束
- **删不掉就报错，不做静默部分删除**：整个过程放在**一个事务**里，任一表失败即回滚。
- 删除顺序：先 `invite`（抢权），再子表。因**无外键**，顺序不影响约束，但抢权必须先做。
- 端上**不得**用本地缓存兜底展示已删除的数据：删除成功后清空页面状态并回首页。

> 保留「删除留痕」与「同意留证」这两类不含内容的数据，是删除权行使的**常见合规例外**（履行举证义务所需），但**必须在《双人数据处理说明》里向用户明示**（见第九节与 ADR-012）。

## 五、决策 4：接口、事务与竞态

### 接口
```
DELETE /api/v1/invites/:code
```
- 用 `:code` 而非 `:id`：**被邀请方视图不保证暴露数值 id**，但双方视图都含 `code`（`InviteInitiatorView.code` / `InviteInviteeView.code`）。
- 权限：`requireParticipant(invite, userId, 'deleteData')` —— 仅 `initiator_uid` 与 `invitee_uid` 可调用；第三人一律按 ADR-004 决策 6 **统一 404**（不泄露「这次配对是否存在」）。
- 状态：**不限制状态**。`invite_created` / `opened` / `consent_given` / `answering` / `completed` / `report_unlocked` / `expired` / `declined` / `cancelled` 均可删（数据控制权无条件）。
- 幂等：删除后再次调用 → `404`（记录已不存在，与越权同码，不区分）。

### 原子抢权（防并发双删）
```
事务开始
  SELECT invite WHERE code = :code            -- 取行并校验参与者
  若不存在或 uid 不是参与者 → 404（回滚）
  DELETE FROM invite WHERE id = :id
  若 affected = 0 → 404（回滚，说明并发中已被删）
  DELETE 子表（answer_sheet / answer_snapshot / report / exclusive_card）
  写 audit_log 留痕
事务提交
```

### 涉隐私自查（铁律 #6：恶意用户会怎么攻击这里）
| 攻击 | 防御 |
|---|---|
| 枚举 `code` 删除别人的配对 | 32 位十六进制邀请码（128 位随机）+ 既有 `invite` 具名限流（C8）+ 必须是参与者 |
| 猜 `code` 探测「配对是否存在」 | 非参与者与已删除**同码 404**，不区分 |
| 并发双删造成部分删除 / 重复留痕 | `DELETE ... WHERE id` 的 `affected rows` 作为原子抢权；全程单事务 |
| 借删除清掉自己刷量的痕迹 | `audit_log` 保留删除留痕 + `visibility_log` 保留；删除动作本身也计入限流 |
| 通过删除绕过「换人重邀限 1 次」（C7） | 删除后 `replaced_from_invite_id` 指向的行可能已不存在 → 换人计数以 `replaced_from_invite_id` 的**存在性**判定，不因删除而放宽（实现时须保持该口径） |

## 六、决策 5：端上显性化（「配对删除显性化」的落实）

| 位置 | 内容 |
|---|---|
| 配对详情页 底部「数据管理」区块 | 先展示本次配对的**数据摘要**（双方各已答 N 题、报告生成时间），再给「删除本次配对数据」按钮 —— 让用户在删之前先看清要删什么 |
| 二次确认弹窗 | 逐条列出「将删除 / 将保留」（对齐决策 3 的两张表，用用户语言表述），并要求**勾选**「我已知晓，删除后无法恢复」；**勾选前删除按钮不可点**（CTA 与勾选联动） |
| 删除按钮样式 | 危险色 `$zb-color-danger`；确认文案中不得出现「取消」以外的模糊动词 |
| 弹窗必含一句 | 「删除后，对方也无法再看到这次配对的一切内容」 —— 让发起人清楚这是**共有物**，不是只删自己那份 |
| 删除成功 | toast + 清空页面状态 + 返回首页 |
| 隐私与安全检查页 区块④ | 同一入口，路径一致 |

## 八、后果与风险

| 风险 | 缓解 |
|---|---|
| 发起方被对方「一键删除」全部报告，产生客诉 | 二次确认弹窗明确写「对方也无法再看到」；删除后 toast 说明；P1 报告可重新邀请重做 |
| 删除不可逆导致误操作 | 双重确认（看清摘要 + 勾选知晓）；危险色按钮；不做「无确认的一键删除」 |
| 悬空的 `visibility_log.report_id` | 该表只用于审计与风控，不做业务查询；文档中记录该弱关联特征 |
| `replaced_from_invite_id` 指向已删行导致换人链断裂 | 决策 4 攻击面表末行：换人计数按「该列是否有值」判定，不解析被指向的行 |
| 删除后 30 天过期任务扫到残留 | 过期任务按 `status IN (...)` 批量更新，删除行不存在即不受影响（`UPDATE` 天然忽略已删行） |
| 事务内 5 张表删除耗时较长（大报告 JSON） | 单次删除数据量 = 1 次配对；`report` 唯一键保证最多 1 行；无需分批 |

## 九、遗留项（本 ADR 不解决，记录备查）

1. **被邀请方「只撤回自己的答案、保留对方报告」**：P1 不提供（决策 2 的代价）。若 P2 有付费与更细的权益分层，可评估「单方撤回 + 报告降级」。
2. **删除后的通知**：P1 无站内消息通道，删除不通知对方（对方下次打开才发现）。若接入订阅消息，可补一条中性通知。
3. **账号级注销的数据删除**（`account_deletion_request`）与本 ADR 的配对级删除是**两条独立链路**，范围与留痕口径需在实现账号注销时单独对齐，**不要互相复用**。
