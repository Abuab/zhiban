## 一、背景

### 1. 现象与缺口（均经代码核实）

| # | 事实 | 出处 |
|---|---|---|
| 1 | 知情同意接口**只改状态**：`consent()` 在 `agreed=true` 时仅 `UPDATE invite SET status='consent_given'`；`agreed=false` 时仅置 `declined` + `declined_at` | `invite.service.ts` L479-519 |
| 2 | `invite` 表**没有任何同意列**（无同意时间、无文案版本） | `schema.sql` L185-212 |
| 3 | 代码注释声称「前端展示与服务端留痕（consent_given 时的 `audit_log`）用同一常量」，但**实际从未写入 audit_log** | `invite.constants.ts` L100 vs L494-497 的 `logger.log` |
| 4 | `audit_log` 的写入是**旁路**：`AuditLogService` 明确「写入失败不得阻断业务」并 `try/catch` 吞掉异常 | `audit-log.service.ts` L63-71 |
| 5 | `user.privacy_policy_version` 是**账号级**（隐私政策），无法承载**配对级**（本次双人数据共同处理）的同意 | `schema.sql` L30 |
| 6 | **发起方的同意从未被采集**：`CreateInviteDto` 只有 `scaleCode`，创建邀请不记录任何同意动作 | `dto/invite.dto.ts` L24-33 |
| 7 | R8 原文写的是「**双方**答题前均须勾选知情同意」，而状态机只建模了被邀请方的同意 | 第 225 行 vs `invite.constants.ts` L60-72 |

**结论**：目前**无法举证**「谁、在什么时间、在哪个版本的文案下、同意了还是拒绝了」。这既是合规缺口（R8 要求强制勾选即意味着需要留证），也是事实 6 的产品缺口（发起方从未被明确告知/同意「自己的 L2 摘要会给对方看」）。

### 2. 为什么不能只写 `audit_log`

事实 4 是决定性的：`audit_log` 的定位是**旁路审计**（写失败静默吞掉、可设保留期、只用于事后追溯），而同意留证需要**稳定存在且可查询**。把合规证据放在一个「写失败不报错、未来可能按保留期清理」的表里，等于没有留证。

## 二、决策 1：新增 `consent_log` 表（append-only、一表多类型）

```sql
DROP TABLE IF EXISTS `consent_log`;
CREATE TABLE `consent_log` (
  `id`             BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  `user_id`        BIGINT UNSIGNED NOT NULL              COMMENT '同意主体',
  `consent_type`   VARCHAR(32)     NOT NULL              COMMENT 'invite_data 双人数据处理；预留 privacy_policy',
  `invite_id`      BIGINT UNSIGNED DEFAULT NULL          COMMENT '配对级同意的关联邀请；账号级同意为 NULL',
  `role`           VARCHAR(16)     DEFAULT NULL          COMMENT 'initiator / invitee（配对级必填）',
  `policy_version` VARCHAR(16)     NOT NULL              COMMENT '同意时的文案版本（端点与说明正文同源）',
  `agreed`         TINYINT(1)      NOT NULL              COMMENT '1 同意 / 0 拒绝（拒绝同样留证，C7 举证用）',
  `ip`             VARCHAR(64)     DEFAULT NULL          COMMENT '真实客户端 IP（resolveClientIp，非代理地址）',
  `user_agent`     VARCHAR(256)    DEFAULT NULL,
  `created_at`     DATETIME        NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  KEY `idx_user_type_created` (`user_id`, `consent_type`, `created_at`),
  KEY `idx_invite` (`invite_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='知情同意留证（append-only；ADR-012）';
```

### 关键约束
- **只追加不更新**：同一人重复同意即多条记录；「当前是否同意」取 `created_at` 最新一条。
- **不建外键**（与全库既有约定一致，`schema.sql` 全文无 `FOREIGN KEY`）；`invite_id` 为应用层弱关联。
- **`user_agent` 截断至 256**（对齐 `audit_log` 的既有处理，防超长插入报错）。
- **写入失败必须阻断业务**（与 `audit_log` 相反）：同意动作若无法留证，则该次同意**不生效**并向用户报错。这是本表存在的全部意义。

## 三、决策 2：同意覆盖**双方**，且分两处采集

| 角色 | 时机 | 位置 | 请求体 |
|---|---|---|---|
| 发起方 | **发起前**（创建配对之前） | 「双人数据处理说明」页底部勾选 + 创建按钮（CTA 与勾选联动） | `POST /v1/invites` 新增**必填** `dataConsentAgreed: boolean`，非 `true` → `10001` |
| 被邀请方 | 打开邀请后、作答前（**既有**） | 既有知情同意页 | `POST /v1/invites/:code/consent { agreed }`（不变） |

### 理由
- R8 原文即「**双方**答题前均须勾选」（事实 7）。
- 发起方也有需要被明确告知的事：**自己单人测评的答案会以「基础摘要（L2）」形式展示给对方**（`InviteInitiatorView` / 三层可见性 R3）。现状是发起方只看到一句分享卡片说明，从未勾选过任何东西。
- 端上已有「双人数据处理说明页」承载长文案；同意动作是两个极短的勾选，不会拉长流程。

### 兼容性
- `POST /v1/invites` 新增必填字段属**契约变更**：小程序端与接口同期发布，无第三方消费者，可接受。
- 白名单校验：只有 `dataConsentAgreed === true` 才创建邀请，不做「缺省视为同意」。

## 四、决策 3：同意文案与版本的承载

| 项 | 内容 |
|---|---|
| R8 原句 | **逐字保留**（ADR-005 已定「R8 原文，逐字一致，禁止改写」，现为常量 `INVITE_CONSENT_TEXT`）：`你们的答案将共同生成一份关系分析；详细分析由发起人持有，你可见基础摘要。` |
| 完整说明 | 《双人数据处理说明》正文（`docs/invite-data-notice.md`，本 ADR 同期起草） |
| 版本常量 | 新增 `INVITE_DATA_CONSENT_VERSION`（`server/src/modules/invite/invite.constants.ts` + 端上 `miniprogram/src/constants/legal.ts`，两处同源；正文文件头部标注同一版本号） |
| 同意页形态 | R8 原句（逐字，突出显示）+ 「我已阅读并同意《双人数据处理说明》」勾选 + 「查看全文」跳说明页 |
| 版本漂移 | **P1 不实现「文案升级 → 进行中的配对重新征得同意」**：配对生命周期仅 30 天，创建时锁定版本；新建配对一律取当前版本。版本升级的重新同意流程记为遗留项（第九节） |

**P5 遗留说明**：`INVITE_CONSENT_TEXT` 目前是**代码常量**（属 ADR-005 已落地的现状），严格地说不符合 P5「可见文案一律落库/可配置」。本 ADR **不扩大范围**去迁移它，只在第九节登记为遗留项；版本号机制先落地，后续迁移文案时版本号不变、正文来源改变。

## 五、决策 4：修正 `consent()` 的注释与实现不一致（缺口 #3）

- `invite.constants.ts` L98-103 的注释由「…服务端留痕（`consent_given` 时的 `audit_log`）…」改为指向 `consent_log`。
- `consent()` 在写 `status` 之后，**同事务**写一条 `consent_log`（`consent_type = 'invite_data'`、`role = 'invitee'`、`policy_version = INVITE_DATA_CONSENT_VERSION`、`agreed = dto.agreed`、`ip`/`user_agent`）。
  —— `agreed = false`（拒绝）**同样留证**：C7「对方拒绝同意」的争议需要能举证，只记 `declined_at` 无法证明用户看到的是哪一版文案。
- 幂等路径（重复点同意）：**不重复写**留证（仅首次 `invite_opened → consent_given` 的那次写入）。

## 六、决策 5：与删除权的关系（承 ADR-011 决策 3）

- 用户行使「删除本次配对数据」时，`consent_log` **不删除** —— 它是「同意曾发生」的举证，不含任何作答内容。
- 这一点**必须在《双人数据处理说明》里向用户明示**（不能只写在 ADR 里）：用户有权删除自己的答案与报告，但「同意记录」会保留。
- 用户**注销账号**时的范围另议（ADR-011 第九节遗留项 3），本 ADR 不覆盖。

## 八、后果与风险

| 风险 | 缓解 |
|---|---|
| `POST /invites` 加必填字段导致老版本小程序创建失败 | 端上与接口同期发布；失败时返回 `10001` 且端上有明确文案（不是静默失败）；老版本会在升级提示内被引导更新 |
| 留证写失败导致同意动作整个回滚，用户看到报错 | 这是**有意为之**（决策 1）：无留证的同意等于没有同意；单表单行插入，实际失败概率极低，报错文案为「服务繁忙，请重试」 |
| `consent_log` 记录 IP 与 UA 引发「过度收集」质疑 | 与隐私政策第一章已声明的「设备与访问日志（IP / 设备型号 / 操作系统 / 访问时间）：用于安全风控」同口径；**在《双人数据处理说明》中明示** |
| 用户以为删除配对数据会连同意记录一起删 | 说明页与删除确认弹窗均明示「同意记录会保留」 |
| `role` 冗余（可由 `invite_id` + `user_id` 推出） | 有意冗余：`consent_log` 需在 `invite` 行被删除（ADR-011）后仍可独立解释，不能再依赖邀请行推断角色 |
| 一表多类型导致后续字段膨胀 | 已有 `policy_version` / `agreed` / `role` 三个通用列；新增类型若需要更多字段，应新建表而不是继续加列（写入 ADR 时再议） |

## 九、遗留项

1. **文案版本升级的重新同意流程**：P1 不实现（决策 3）。若后续《双人数据处理说明》发生实质性变更，需补「进行中配对如何处置」的裁决。
2. **`INVITE_CONSENT_TEXT` 从代码常量迁移到站点域配置（`sys_config`）**：符合 P5，但会牵动 ADR-005 的既有实现，单独排期。
3. **账号注销时的 `consent_log` 处置**：与配对级删除不同，需在实现账号注销时单独裁决。
4. **发起方同意的文案**：本 ADR 用同一份《双人数据处理说明》承载双方同意（R8 原句只描述了被邀请方视角）。若认为发起方需要一段**独立措辞**，需产品负责人追加确认。
