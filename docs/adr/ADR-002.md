# ADR-002：新增站点级配置域（sys_config）与品牌名可配置

| 项 | 内容 |
|---|---|
| 编号 | ADR-002 |
| 状态 | accepted（2026-09-19 用户裁决） |
| 日期 | 2026-09-19 |
| 关联规格 | 宪章 P5「内容与规则可配置」、P6「一人可运营」、宪章第六部分「待拍板决策点 1：品牌名」、实施路线图 §〇《可配置项注册表》 |
| 决策人 | 用户（产品负责人） |

---

## 一、背景

`docs/constitution.md` 第六部分把「品牌名」列为**待拍板 Blocking 决策点**（3 个候选未最终确定）。同时宪章 P5 与实施路线图 §〇 要求「一切可变的东西都不许进代码」，其中明确点名「页面文案」。

但《可配置项注册表》的 7 个配置域（量表 / 计分 / 报告 / 商品 / 内容 / 运营 / 功能开关）**没有「站点级 / 品牌」域**，导致品牌名既属于「必须可配」的精神，又没有落库位置。

用户 2026-09-19 明确要求：**把品牌名做成管理后台可自定义配置项**。

---

## 二、决策 1：新增通用站点配置表 `sys_config`

### 选项
| 选项 | 说明 |
|---|---|
| A. 复用 `feature_flag` | 零 schema 改动；但该表语义是「全局开关」，混入文案会让开关类查询与后台页面变脏 |
| B. 新建专用「品牌配置」字段 | 改动最小；但后续每加一个站点级配置（客服微信、运营主体名、隐私政策生效日期）都要再改表 |
| C. **新增通用键值表 `sys_config`** | 品牌名只是其中一条；后续站点级配置零 schema 改动 |

### 决定
**采用 C。** 表结构见 `docs/schema.sql` 第九部分（`sys_config`）。

关键字段：
- `config_key`（唯一）：点分层级，如 `brand.name`
- `config_value`：统一存字符串，类型由 `value_type` 解释（string / number / boolean / json）
- `config_group`：分组，供后台分页签展示（brand / site / contact …）
- `is_public`：**是否允许经免鉴权接口下发，默认 0（fail-closed）**
- `updated_by` / `updated_at`：变更留痕，供模块 8 后台审计

### 理由
- 与 P6「一人可运营」一致：新增一条文案 = 后台加一行，不动表不动代码。
- 与既有表风格一致（`sensitive_word` / `feature_flag` / `ops_slot` 均为键值或轻量配置表）。

### 后果
- 《可配置项注册表》实际扩展为 **8 个域**（新增「站点域」），本文档即该扩展的规格补丁。
- 该表容量极小（预计 <50 行），无需分页与索引优化。

---

## 三、决策 2：公开配置走独立免鉴权接口 + `is_public` 闸门

### 问题
品牌名在**登录前**就要展示（登录页标题、授权弹窗、隐私政策页、导航栏），此时用户没有 token，无法调用需鉴权的接口。

### 决定
1. 新增 `GET /api/v1/config/public`，`@Public()` 免鉴权，仅返回 `is_public = 1` 的键值。
2. **`is_public` 默认 0**，只有显式置 1 的键才会下发。规则：仅「面向全体用户的非敏感展示文案」可置 1；任何凭据、内部阈值、客服内部联系方式一律保持 0。
3. 返回值按点号分层为嵌套 JSON（`brand.name` → `{"brand":{"name":"…"}}`），便于前端直接取值。
4. 键名须匹配 `^[a-z][a-z0-9_]*(\.[a-z][a-z0-9_]*)*$`，非法键跳过并告警——防止 `__proto__` 一类的键名污染返回对象。
5. 接口按 IP 限流（与登录接口同维度），防爬。

### 为什么不做 Redis 缓存
`sensitive_word` 需要缓存是因为它在**每次昵称更新**时都要查；而公开配置**每次冷启动只查一次**（低频），且表内行数极少。加缓存只会引入「运营改完品牌名 5 分钟内不生效」的陈旧问题，收益为负。ADR-001 §五第 3 条的缓存策略针对的是量表/计分/开关，不适用于本表。

---

## 四、决策 3：本期生效范围限定为「运行时展示文案」

### 决定
本期（用户裁决）只让**运行时展示文案**跟随配置：登录页主标题、授权弹窗文案、隐私政策页标题、首页导航栏标题（`uni.setNavigationBarTitle`）。

**明确不做**：
| 不做的项 | 原因 |
|---|---|
| `manifest.json` 的 `name` / `description` | 编译期元信息，改了必须重新发版，与「零发版」矛盾；且小程序对外展示名称由**微信公众平台**控制，与代码无关 |
| 隐私政策正文里的品牌署名 | 政策中的**运营主体**（个体户/公司法定名称）不应随品牌名变化，两者必须在文案中区分；隐私政策为需留痕的合规文本，改动应走版本号升版流程 |
| 代码注释与运行日志里的「知伴」 | 属于工程标识而非产品文案；跟随配置会让排查日志时无法定位产品 |

### 后果
- 小程序端保留编译期兜底常量（`pages.json` / `manifest.json` 里的「知伴」不删），运行时由接口值覆盖。
- 若将来要改小程序对外名称，仍需在微信公众平台操作 + 重新发版，这是平台约束，非本方案缺陷。

---

## 五、决策 4：前端必须有兜底值，接口失败不得阻塞启动

- 小程序端内置兜底品牌名常量；`GET /config/public` 失败时**静默降级**用兜底值渲染，不弹错误提示、不阻塞隐私政策弹窗与登录流程（边界总表 A5「不出现死页」）。
- 品牌名不落本地存储：仅在内存持有，避免引入「本地缓存了旧品牌名」的一致性负担。

---

## 六、总后果与风险

| 风险 | 缓解 |
|---|---|
| 运营误把敏感配置置为 `is_public = 1` 导致泄露 | 列默认值 0（fail-closed）；模块 8 后台编辑页对该开关加显式说明与二次确认 |
| 品牌名被改成空字符串导致页面标题缺失 | 服务端不校验但前端做空值兜底（`trim()` 后为空则用常量）；模块 8 保存时做非空校验 |
| 品牌名与隐私政策署名不一致造成合规瑕疵 | 本 ADR §四已明确二者分离；隐私政策改动仍走版本号升版 |
| 新增配置域未同步到宪章 | 本文档即规格补丁；宪章第六部分「品牌名」决策点在品牌名最终确定后回填 |
