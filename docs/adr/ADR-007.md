## 一、背景

模块 6（支付与权益）与模块 7（锦囊卡片流）开工前，发现 **1 处规格冲突 + 1 处规格缺口 + 2 处实现方未定**：

| # | 议题 | 规格要求 | 冲突/缺口 |
|---|---|---|---|
| 1 | **模块 6 范围** | prompt.md 第 101-103 行要求完整支付链路（预下单 / 回调验签+幂等 / 对账 / 退款 / 兑换码），完成标准「沙箱走通全链路 + 伪造回调被拒」 | 宪法 §2.5 明确「**P1 阶段：全免费，不接支付**」。优先级规则：宪法 > 其他 → **互斥**。且当前无微信支付商户号/APIv3 密钥/商户证书，真实沙箱不可达 |
| 2 | **专属卡触发时机** | 增补 v0.3 §二「专属卡生成仅在**付费解锁后**触发；免费用户见通用卡 + 锁定占位」 | P1 全免费 → 「付费解锁」这一前置条件在 P1 不存在，需另定触发条件 |
| 3 | **大模型供应商** | 增补 v0.3 §二「服务端调用大模型 API 生成」；§9.2 给了完整 prompt 模板 | 规格未指定供应商；`server/.env.example` 已预留 `LLM_API_BASE / LLM_API_KEY / LLM_MODEL`，代码未实现 |
| 4 | **单人用户的专属卡** | §9.2 的 prompt 模板要求注入「**双方**维度得分、16 型类型、分歧题目及双方选项」 | 定价 v0.2 却写议题包「付费方：**任何用户**」→ 单人用户付费后无 prompt 输入数据，**规格缺口** |

## 二、决策 1：模块 6 = 权益域完整落地 + **可切换支付网关**（P1 默认免费直发）

### 选项
| 选项 | 说明 |
|---|---|
| A. **权益域 + 可切换网关** | 权益/订单/兑换码全部落地；支付层按微信支付 V3 协议实现验签、幂等、查单、退款、对账，但网关实现可由配置切换（`free` / `mock` / `wechat`）。P1 默认 `free` |
| B. 仅权益域，支付代码整体留 P2 | 不写任何订单与支付代码。最贴合宪法，但模块 6 完成标准（伪造回调被拒）无法验证 |
| C. 完整接入真实微信支付 | 依赖商户号与证书，当前不可达 |

### 决定
**采用 A（产品负责人裁决）。**

支付网关抽象为 `PaymentGateway` 接口，三个实现按 `PAYMENT_GATEWAY` 环境变量切换：

| 值 | 行为 | 用途 |
|---|---|---|
| `free`（P1 默认） | 下单即视为到账，直接发权益，**不生成支付参数** | P1 全免费，走通「订单 → 权益」链路 |
| `mock` | 返回可前端调起的模拟支付参数；回调走**同一套验签 + 幂等**代码路径 | 验证「伪造回调被拒」「重复回调幂等」「查单补单」 |
| `wechat` | 微信支付 V3（JSAPI 下单 / 回调验签 / 查单 / 退款） | P2 接真实商户号，仅需改配置 + 填密钥 |

**关键约束（不得违反）**：
- 金额一律取自 `product.price`，请求体中的金额字段**只作展示、绝不采信**（E4 / PRD-005 §2）。
- 回调处理必须「先落 `payment_notify_log` 再改单」，验签失败的报文也必须留证（`verify_result = 0`）。
- 幂等键为 `out_trade_no`：命中已处理订单时**直接返回 success**，不重复发权益（E2）。
- 商品快照写入 `order.product_snapshot`，改价不影响历史订单（E6）。
- 支付网关**不做任何自动重试**；漏单由「每日对账 + 用户端恢复购买」兜底（E1）。
- P1 免费模式下**不存在真实扣款**，退款/对账仍按 E1/E10 保留代码路径与后台入口。

## 三、决策 2：专属卡由**用户显式点击**触发生成

### 选项
| 选项 | 说明 |
|---|---|
| A. **用户点击生成** | 卡片流最后一卡显示「生成你们的专属版本」，点击才调模型；生成一次后落库缓存 |
| B. 进入议题包自动生成 | 体验最顺，但每进一个新议题都产生一次模型调用，P1 免费期成本不可控 |
| C. 本期只做锁定占位 | 不接模型，专属卡位置显示锁形占位 |

### 决定
**采用 A（产品负责人裁决）。**

- 保留规格「付费解锁后触发」的**位置语义**：入口仍在卡片流最后一卡，只是 P2 上线时把「点击即生成」改为「先校验权益再生成」。
- 缓存唯一键沿用 `exclusive_card.uk_invite_topic(invite_id, topic_id)`：**同一邀请同一议题只生成一次**，二次进入读缓存（§9.3）。
- 生成结果必须过敏感词/P7 禁词校验才展示；校验失败自动重试 1 次，再失败降级为通用版并记 `status = 'degraded'`（§9.3）。
- 生成行为写 `audit_log`（viewer / 时间 / prompt 版本），`exclusive_card.prompt_version` 与 `model` 一并落库。

## 四、决策 3：大模型供应商取 **DeepSeek**（OpenAI 兼容协议）

### 选项
| 选项 | 说明 |
|---|---|
| A. **DeepSeek** | `api.deepseek.com`，`deepseek-chat`，OpenAI 兼容，单次约 ¥0.001-0.01 |
| B. 阿里通义千问 DashScope | 需另装 SDK 或走兼容模式 |
| C. 智谱 GLM | 同上 |
| D. 暂不接，先留桩降级 | 接口与缓存链路完整，填入 Key 即生效 |

### 决定
**采用 A（产品负责人裁决）**，配置项复用已预留的 `LLM_API_BASE / LLM_API_KEY / LLM_MODEL`。

**关键约束**：
- 调用方必须是**服务端**（§9.3），API Key 只存 `server/.env`，**禁止**进代码库、禁止下发端上。
- 走 OpenAI 兼容的 `POST {LLM_API_BASE}/chat/completions`，不引入厂商 SDK（减少依赖与版本风险）。
- 超时与失败**一律降级**（`status = 'degraded'`，展示通用卡内容），**不向用户暴露模型错误原文**。
- `LLM_API_KEY` 为空时视为「未配置」：接口直接返回降级结果，不报错、不阻塞内容浏览。

## 五、决策 4：单人场景**降级为单人版专属卡**，完成双人邀请后可重新生成覆盖

### 选项
| 选项 | 说明 |
|---|---|
| A. **降级为单人版** | 有已完成邀请 → 双人版 prompt（双方分数/16 型/分歧题）；无邀请 → 单人版 prompt（本人维度分 + 16 型） |
| B. 提示先邀请对方 | 严格贴合 §9.2，但单人用户拿不到专属卡 |
| C. 单人直接用通用卡 | 单人场景不调模型 |

### 决定
**采用 A（产品负责人裁决）。**

- prompt 模板分两版，共用同一接口与缓存：`premium-v1-duo`（双人）/ `premium-v1-solo`（单人），落 `exclusive_card.prompt_version`。
- **降级为单人版不等于降低合规要求**：两版 prompt 均使用 §9.2 的系统角色设定与自检条款（中立、不评判、不劝分、不制造焦虑、不提供法律意见）。
- 单人版**不编造对方数据**：只注入本人数据，输出面向「如何向伴侣开口」的建议。
- 用户后续完成双人邀请时，可**手动重新生成**覆盖缓存（`exclusive_card.prompt_version` 由 solo 更新为 duo，`content` 覆盖），不存在自动改写已生成内容的路径（§二「题库/模板升级不溯及已生成内容」）。

## 六、附带技术决策

| # | 议题 | 决定 | 依据 |
|---|---|---|---|
| 1 | 8 个议题的编码 | 语义化 snake_case：`betrothal_gift` / `money` / `chores` / `second_child` / `in_law_boundary` / `cold_war` / `long_distance` / `meet_parents` | §9.5 示例用 `"licai"` 与其实际议题（彩礼/管钱/…）不对应，属示例残留；编码需一眼可读 |
| 2 | 卡片类型落库值 | `pitfall` / `script` / `quiz` / `cognition` / `action`（`exclusive` 不落 `topic_card`，由 `exclusive_card` 表承载） | `topic_card.type` 注释已列全 6 值；专属卡是**每邀请动态生成**的，无法预置为静态卡 |
| 3 | 阅读进度 | `topic_read_progress` 按 (user_id, topic_id) 唯一，记录 `last_order_no` 续看位置与 `finished` 打卡 | §9.4「已读进度本地记录」→ 改为**服务端记录**，理由：换设备（A1）后进度不丢，且成本极低（一行一议题） |
| 4 | 议题包 → 报告挂载 | `topic.mount_dimensions` 存维度编码数组；报告页「待沟通区」按维度反查议题包入口 | 增补 v0.3 §三「报告中每个待沟通区 → 对应议题包入口」 |
| 5 | 订单超时关闭 | 30 分钟（`order.expire_at`），由 BullMQ 定时任务扫描 `status = 'created'/'paying'` 且已过期者置 `closed` | E3；关闭后用户可重新下单 |
| 6 | 每日对账 | 定时任务对账「本地 `paid` 订单 vs 网关侧订单」，差异落 `job_task`（`type = 'pay_check'`）转人工 | E1；P1 免费模式下对账结果恒为空，但代码路径保留 |

## 八、后果与风险

| 风险 | 缓解 |
|---|---|
| P1 免费让「支付链路」长期不被真实流量验证 | 网关接口经 `mock` 模式单测覆盖（验签失败、重复回调、金额篡改、超时关闭、查单补单），并用 `PAYMENT_GATEWAY=mock` 在服务器做一次端到端演练 |
| P2 接真实商户号时出现协议偏差 | 微信 V3 实现按官方文档写全（签名串拼装、`WECHATPAY2-SHA256-RSA2048`、平台证书验签），密钥缺失时**启动即拒绝**启用 `wechat` 模式（fail-fast） |
| 专属卡模型调用成本不可控 | 用户显式点击 + 每邀请每议题一次缓存 + 单次超时 + 未配置 Key 直接降级；生成次数可通过 `audit_log` 统计 |
| 模型输出触碰 P7 禁词 | 生成后过 `SensitiveWordService(scope = 'exclusive_card')`，失败重试 1 次再降级，原文不展示不落库（`check_result` 记命中词） |
| 免费期权益被滥用 | 权益仍走「订单 → 入账」链路（`source = 'order' / 'coupon' / 'manual'`），有据可查；`entitlement` 唯一约束防重复发放 |

## 九、迁移与运维

- **无 schema 变更**：模块 6/7 全部 9 张表在 `docs/schema.sql` 中已建，本 ADR 不新增列、不改列。
- 商品种子：`cd /opt/zhiban/server && docker compose exec api node dist/scripts/product-seed.js`（幂等 upsert）。
- 议题种子：`docker compose exec api node dist/scripts/topic-seed.js`（幂等 upsert，按 `topic.code` + `(topic_id, order_no)`）。
- 环境变量（P1）：
  ```
  PAYMENT_GATEWAY=free
  LLM_API_BASE=https://api.deepseek.com/v1
  LLM_API_KEY=<填入后专属卡才可用>
  LLM_MODEL=deepseek-chat
  ```
- 切到 mock 演练：`PAYMENT_GATEWAY=mock` → 重启 → 走通「下单 → 模拟回调 → 权益到账 → 重复回调幂等 → 伪造回调 401」。
