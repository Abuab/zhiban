## 一、背景

模块 4（单人测评流程，prompt.md 第 86-89 行）要求：答题流程（断点续答 B1、进度、敏感维度前置同意 B7）、简版报告生成、付费墙锁定占位。开工前发现 **3 处规格已要求但 schema 未留位置** 的缺口：

| # | 缺口 | 规格要求 | 现状 |
|---|---|---|---|
| 1 | **卷首文案无处落库** | constitution.md 第 293 行给出婚前评估卷首作答说明；第 408 行给出底线题组卷首文案 | `scale_version` 表无对应列；模块 3 的题库种子 `ScaleVersionSeed.introText` 因此**被静默丢弃**，未写库 |
| 2 | **敏感维度跳过状态无处落库** | B7：亲密维度拒绝授权 → 跳过该维度、报告标注"未评估"、允许事后补答；A-4：补答后报告标记"补测" | `answer_sheet` 无记录跳过维度的列；`dimension_scores_json` 虽可缓存分数但**无法区分「未评估」与「已作答得 0 分」** |
| 3 | **单人简版报告文案的承载表未指定** | 价值感与内容标准 §一：简版对照 = 维度一句话点评 ≤30 字；P5 要求报告文案可配置 | architecture.md §5 已指定报告域落 `report_template` / `report_template_block`，但**单人模板的 `level` 取值与 block 编码约定未定义** |

按铁律 #2（规格没写清 → 列选项让用户选）提交产品负责人裁决，结论为：**补两处列 + 写 ADR-004**。

## 二、决策 1：`scale_version` 增 `intro_text` 与 `baseline_intro_text`

### 选项
| 选项 | 说明 |
|---|---|
| A. **给 `scale_version` 增两列** | `intro_text`（整卷卷首说明）+ `baseline_intro_text`（底线题组卷首文案）；由题库导入脚本写入 |
| B. 只增 `intro_text` | 底线题组文案由小程序前端常量承载 |
| C. 都不增 | 两者都由小程序前端常量承载 |

### 决定
**采用 A。**

### 理由
- 宪章 P5 是宪法级原则，原文即「任何硬编码进代码的题/文案 = 工程事故」。卷首文案属于**内容**而非**判定规则**，必须可后台配置、改文案零发版。
- 底线题组是「独立呈现」的分组（题库第 406 行），其卷首文案与整卷卷首文案**并列存在**且不同，放在同一列会互相覆盖，故必须两列。
- 模块 3 的 `ScaleVersionSeed` 已经带着 `introText` 字段，只是没有落库位置 —— 本决策是把已存在的设计意图补完，不是新增需求。
- 选项 B/C 都会把「运营改一句话」变成「发版」，与 G1 验收（改一处文案零发版）冲突。

### 实现要点
- 列定义：`intro_text VARCHAR(512) DEFAULT NULL`、`baseline_intro_text VARCHAR(512) DEFAULT NULL`。
- 类型：`ScaleVersionSeed.baselineIntroText` 为 `string | null`（16 型量表无底线题组，取 `null`）。
- 导入服务写入这两列；**已导入的版本需要一次回填**（模块 3 导入时被丢弃），故本 ADR 附带在服务器执行 `ALTER TABLE` + 重跑 `npm run scale:seed`。
  - 因 `scale_version` 已存在时种子服务会「跳过导入」，回填需临时以 `--force` 重建，或直接 `UPDATE` 两列。**采用后者**：`--force` 会重建题目行（`scale_question.id` 变化），而 `answer_sheet.scale_version_id` 指向版本而非题目，虽无外键但会让历史题目行 id 漂移，风险大于收益。

## 三、决策 2：`answer_sheet` 增 `skipped_dimensions_json`

### 选项
| 选项 | 说明 |
|---|---|
| A. **增 `skipped_dimensions_json JSON`** | 显式记录被拒绝授权的维度编码数组，如 `["INTIMACY"]` |
| B. 复用 `dimension_scores_json` 的空值推导 | 维度无有效答案即视为未评估，不额外记录 |
| C. 只存 Redis 草稿 | 交卷后丢弃跳过决策 |

### 决定
**采用 A。**

### 理由
- B 的致命缺陷：`(均分 - 1) × 25` 公式下**全选 1 分恰好得 0 分**，与「未评估」数值相同，无法区分；一旦混淆，报告会把「拒绝授权」误读成「极端取向」，属于对用户真实意愿的错误呈现（P7 劝和基线下尤其不可接受）。
- C 不可行：B7 要求报告长期标注「未评估」，且 A-4 要求保留事后补答入口 —— 丢弃决策就丢失了「哪几维是未评估、补答后要标补测」的判据。
- 显式记录还带来可审计性：F 域要求隐私相关操作可追溯，用户的授权/拒绝行为本身应留痕。
- 存**维度编码数组**而非布尔位图：维度编码是 `scale_dimension.code` 的业务键，跨版本可读；位图依赖维度顺序，题库改版即失真。

### 实现要点
- 列定义：`skipped_dimensions_json JSON DEFAULT NULL`，值为 `string[]`（维度编码），空数组与 `NULL` 等价于「未跳过任何维度」。
- 计分时：被跳过的维度**不参与维度分**，在报告中以 `evaluated: false` 呈现，不写入 `0`；其余维度正常出分（B7「其余 7 维正常出分」）。
- 事后补答（A-4）：补答写入答案后，该维度转为已评估，报告标记 `supplemented: true`（"补测"）。

## 四、决策 3：单人简版报告文案落 `report_template` / `report_template_block`

### 决定

1. **模板行**：`report_template` 插一行 `code = 'SINGLE-PRE-LITE'`、`audience = 'single'`、`scale_version_id` = SCALE-PRE 1.0 的版本 id、`level = 'L1'`、`version = '1.0'`、`disclaimer` = 规格 2.3 固定免责声明原文。
2. **`level = 'L1'` 的语义澄清**：三层可见模型（L1 完整版 / L2 基础版 / L3 分享版）只适用于**双人对比报告**。单人报告只有唯一可见层级，不参与三层过滤，此处 `level` 固定写 `'L1'` 仅因该列 `NOT NULL`。**不新增枚举值、不改列定义**（避免为一个语义占位扩大 schema 变更面）。
3. **block 编码约定**：单人简版报告的 block_key **直接用维度编码**（`FINANCE` / `HOUSING` / … / `INTIMACY`），另加两个非维度 block：
   - `INTRO`：报告开场白
   - `LOCK_HINT`：付费墙锁定占位文案（说明解锁后可获得哪些**类别**的内容，**不含内容本体、不写随数据变化的条数**）
4. **block 排序**：`order_no` 取「维度 `order_no` × 10」，`INTRO` = 10、`LOCK_HINT` = 990。
5. **一句话点评不嵌分数、不做分档**：
   - 规格只定义了**双方差值**的分级阈值（15/30，规则 5），**未定义单人维度分的分档阈值**。故单人点评采用「按维度给一句中性描述」的形式，不引入无出处的分数档位，文案中也不出现"高/中/低"或任何倾向判词（符合 P7）。
   - 分数由报告的**数值字段**（雷达图数据）单独呈现，不塞进文案：否则文案长度会随分数位数（如 `100.0`）波动，突破 ≤30 字的上限。
   - 简版**不嵌昵称**：价值感与内容标准 §一「简版对照」明确「专属感 = 无昵称」，昵称属完整版能力。因此 `INTRO` 文案不含 `{昵称}` 占位符。

### 理由
- 报告文案归属报告域是 architecture.md §5 的既定映射；改用 `sys_config` 承载会让「报告模板」配置页在模块 8 变成空壳，破坏配置域的完整性。
- 不做分档是**刻意的克制**：凭空发明单人分数阈值等于自行修改规格（违反铁律 #1）。分档阈值应由产品在模块 5（双人完整版 300-500 字维度解读必须分档）时一并定义，届时以新 ADR 补充。

### 后果
- 模块 5 的完整版维度解读会**真正需要**分档阈值 → 记入待办，模块 5 开工前必须先裁决。
- 模块 8 的「报告模板」页需支持按 `audience` / `level` 筛选模板，并支持 block 的增删改（本期未做，属模块 8 剩余范围）。

## 五、决策 4：交卷后答案不可改，但保留敏感维度补答通道

### 决定
- `answer_sheet.status` 为 `submitted` 后，**普通答案一律拒绝修改**（B5「提交后锁定不可改」，返回 `ANSWER_LOCKED(30003)`）。
- **唯一例外**：`POST /api/v1/assessments/{id}/supplement` 仅允许补答 `skipped_dimensions_json` 中被跳过的维度（A-4）。补答后重新计分，该维度转为已评估并标记「补测」。
- 草稿保存（`PUT /api/v1/assessments/{id}/draft`）使用 `draft_version` 乐观锁防多端覆盖（A3）：请求需带上本地 `draftVersion`，与库中不一致即返回冲突错误，不静默覆盖。
  - 用 `PUT` 而非 `PATCH`：微信小程序 `wx.request` 的 `method` 合法值不含 `PATCH`（仅 OPTIONS/GET/HEAD/POST/PUT/DELETE/TRACE/CONNECT），选 `PATCH` 会导致端上无法发出请求。

### 理由
- B5 与 A-4 表面冲突（一个要锁、一个要补），实为不同对象：B5 锁的是**已作答的题**，A-4 放开的是**当时被拒绝授权、根本没作答的维度**。以「仅允许补答被跳过维度」精确表达这个边界，既守住快照严肃性，又兑现 B7 的补答承诺。
- `draft_version` 乐观锁是 A3（同一微信多设备）的最小实现，避免「新设备覆盖旧设备已答内容」。

## 六、决策 5：计分规则对量表版本是**可选**的（装载层不得强制要求）

### 背景（部署期实测发现的缺陷）
服务器首轮端到端验证时，`POST /api/v1/assessments {scene:"p16"}` 直接失败：

```
{"code":30001,"message":"量表版本 2 缺少生效中的计分规则，无法计分"}
```

而该状态是**正常种子结果**：`scripts/seed-scale.ts` 的 `SCALE_CODES_NEED_SCORING_RULE` 只含 `SCALE-PRE`
（16 型以四维端点组合出类型，不产出 0-100 维度分）。即：**在完全按标准流程播种的库上，16 型永远开不了卷**。
单测未发现是因为 `makeP16Bundle()` 夹具**凭空给了 16 型一条计分规则**，与生产事实不符。

### 选项
| 选项 | 说明 |
|---|---|
| A. **计分规则改为可空，由消费方按场景判定** | `ScaleBundle.scoringRule/engineRule` 允许为 `null`；装载层不判断必要性；婚前评估分支在使用前显式校验 |
| B. 给 SCALE-16P 也播一条计分规则 | 让库满足装载层的前提条件 |
| C. 装载层按「是否有计分维度」推断是否必需 | 用 `is_scored` 等数据特征代替显式声明 |

### 决定
**采用 A。**

### 理由
- 16 型的类型判定（规则 8：每维 6 题、A 端 ≥4 取 A、≤2 取 B、=3 平局取 B）**根本不读计分规则**；为它插一行无意义数据属于「用数据迁就代码」，且会让模块 8 的计分规则配置页出现一个无法解释的空壳行。
- B 还会把「规则缺失」这类真实部署事故的信号稀释掉：一旦所有版本都有规则行，`scoring_rule` 缺失就无法再作为运维告警。
- C 不可取：是否产出维度分是**场景/量表语义**，不是能从列数据可靠推导的性质；用数据特征隐式推断会把「是否需要规则」变成不可读的魔法。
- A 保留了 fail-closed：真正需要规则的分支（婚前评估）在使用前显式校验并抛 `SCALE_NOT_FOUND(30001)`，缺失仍是**响亮失败**而不是产出无维度分的半份报告。

### 实现要点
- `ScaleBundle.scoringRule: ScoringRuleEntity | null`、`engineRule: ScoringRuleConfig | null`；`loadBundle` 删除强制抛错，改为 `scoringRule ? toScoringRuleConfig(scoringRule) : null`。
- `assessment.service.ts` 的 `computeScores`：16 型分支提前 return（不触规则）；婚前评估分支取 `bundle.engineRule` 后**显式判空并 error 日志 + 抛错**。
- 夹具与生产对齐：`assessment.service.spec.ts` 的 `makeP16Bundle()` 改为 `scoringRule: null, engineRule: null`，使已有的 16 型用例（24 题取卷、四维 A 端命名、平局判 B 端）**天然成为本缺陷的回归保护**。

### 后果
- 模块 3 的 `ScaleBundle` 契约放宽（唯一消费方是测评域，改动面可控）。
- 「计分规则缺失」不再由装载层统一拦截，任何新场景接入时必须自行确认是否需要规则 —— 已在 `loadBundle` 的注释中写明该约定。

## 七、决策 6：资源越权与「资源不存在」返回同一错误（消除 id 枚举 oracle）

### 背景（部署期实测发现的缺陷）
端到端验证时，用 B 账号访问 A 账号的答题卷返回 `{"code":10004,"message":"无权访问该答题卷"}`，
而「不存在的 id」返回 `10002`。两者可区分 ⇒ 攻击者持合法登录态、用自增 `id` 逐个探测，
即可从错误码差异判断哪些答题卷 id 真实存在（**枚举 oracle**：泄露平台业务量，属信息泄露的低危项）。

同时发现 `10004` 在 `ErrorStatus` 中**未映射**，实际返回 HTTP 400，而接口文档写的是 403 —— 契约与实现也不一致。

### 选项
| 选项 | 说明 |
|---|---|
| A. **两者合并为 `10002`（404）** | 非本人与不存在返回同一错误；越权仍记 warn 日志供告警 |
| B. 保持区分，只把 `10004` 的 HTTP 状态码修成 403 | 最小改动，保住诊断信息 |
| C. 非本人返回 `10004`（403），不存在返回 `10002`，并额外加探测限流 | 用限流对冲枚举 |

### 决定
**采用 A。**

### 理由
- 宪章 F4（P0）要求的是「逐请求校验资源归属 + 越权尝试记日志/告警」，**未要求**对外区分两类失败；
  区分是本次实现自行引入的信息，去掉它不违反任何规格。
- 可观测性不需要靠响应体承载：越权尝试照常打 warn 日志（含 `sheetId` 与访问者 `userId`），
  运维侧反而比用户侧看得更全 —— 把差异留在服务端、不给调用方，是资源归属校验的标准做法。
- B 保留了 oracle，属「为了诊断信息牺牲一层防护」，而诊断信息已由日志满足，收益为零。
- C 增加复杂度且只是把「可直接枚举」变成「慢速枚举」，未消除问题；限流是另一层防线，不该用来补这个洞。
- 客户端无感：端上对两者本就同处理（提示并返回首页），合并不产生行为差异。

### 实现要点
- `requireOwnedSheet` 的两条分支同抛 `RESOURCE_NOT_FOUND(10002)`，越权分支保留 warn 日志。
- `business.exception.ts` 补上 `[ErrorCode.FORBIDDEN]: HttpStatus.FORBIDDEN`
  （该映射此前缺失，导致 `10004` 落到 400 兜底，与文档不符；`FORBIDDEN` 仍可用于「已登录但无权限」的其他语义场景）。
- `docs/api.md` §12 的错误码表把两行合并为一行；控制器注释与小程序接口层注释同步。
- 单测 `访问他人答题卷一律拒绝，且不透露「这份卷属于别人」` 的断言由 `FORBIDDEN` 改为 `RESOURCE_NOT_FOUND`
  （该用例标题本就写着「不透露」，此前断言与之自相矛盾）。

### 后果
- **模块 5（双人邀请与对比报告）沿用同一约定**：报告/邀请资源的越权访问必须与「不存在」返回同一错误。
  尤其对比报告涉及双方数据（2.4 隐私约束），枚举 oracle 的后果比单人测评更重。

## 八、总后果与风险

| 风险 | 缓解 |
|---|---|
| 三处 schema 变更需在生产执行 `ALTER TABLE` | 均为**纯增列且可空**，无默认值回填、无索引变更，对存量 0 行表（`answer_sheet` 当前为空）与已有 2 行 `scale_version` 均零风险；执行前 `mysqldump` 备份 |
| 单人简版报告「一句话点评」文案偏中性、信息量低于完整版 | 与规格一致：简版本就是「一句话点评 ≤30 字」的免费态，完整版价值差正是付费/解锁动机（价值感标准 §三 信息差可视化） |
| `level = 'L1'` 被后续开发者误读为「双人完整版」 | 本 ADR 明确语义；`audience` 字段是真正的分流依据，过滤必须先看 `audience` 再看 `level` |
| 单人分档阈值长期缺失导致模块 5 重复返工 | **已消解**：ADR-005 决策 2 裁定完整版维度解读**按差值等级**分档（复用 R1 的 15/30，零新增阈值）；单人简版维持本 ADR 决策 3.5「不做分档」 |
| `skipped_dimensions_json` 被前端伪造（未真拒绝授权却声称跳过） | 跳过只影响**本人报告**的可见维度，不产生跨用户数据泄露；且跳过使本人少填题、不获得任何额外权益，无攻击收益 |
| 计分规则改可空后，新场景漏校验导致拿 `null` 计分 | 唯一消费点已显式判空抛错（fail-closed）；夹具与生产对齐后 16 型用例即为回归保护 |
| 夹具与生产数据不一致导致缺陷在单测层隐形 | 本轮已发生一次（16 型夹具多给一条计分规则）。约定：**场景夹具必须取自种子脚本的真实产物**，不得为「让测试跑通」补数据 |
