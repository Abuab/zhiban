## 一、背景

模块 6 服务端（订单 / 权益 / 兑换码 / 回调 / 定时任务 / 后台切片）已落地并验证；补端上接入时发现两处规格不清：

| # | 议题 | 规格原文 | 缺口 |
|---|---|---|---|
| 1 | **P1 免费期 iOS 是否隐藏「领取」** | PRD-005 §4「iOS 端隐藏所有购买按钮（商品表配置 `ios_visible=false`）」 | P1 全免费（ADR-007 决策 1：所有商品 `price = 0`、下单即到账、端上**不存在任何支付动作**）。若照字面隐藏，iOS 用户连免费权益都领不到（含 AI 专属卡的解锁前提）；而 §4 的立法目的是避开 Apple 对**虚拟商品支付**的限制，`price = 0` 时该风险不存在 |
| 2 | **端上页面形态** | 宪法《配置项注册表》只登记了「商品域」的**后台**页面；端上页面切分无规格 | 接口层已备好 7 个端点（商品列表 / 权益汇总 / 下单 / 我的订单 / 订单详情 / 恢复购买 / 兑换码）。P1 商品全免费，`products` 的信息量（名称 + ¥0 + 权益）撑不起独立「定价页」，拆两页会多一层无内容可放的空跳转 |

> 两处皆属「规格没写清」，按 prompt.md 铁律第 2 条**列出选项交产品负责人裁决**，不擅自发明。

---

## 二、决策 1：P1 免费期（`price = 0`）**豁免** iOS 隐藏，免费商品照常展示「领取」

### 选项
| 选项 | 说明 |
|---|---|
| A. **免费期豁免** | `price = 0` 时不看 `iosVisible`，iOS 也展示「免费领取」；P2 恢复真实价格后自动回到 `iosVisible` 逻辑 |
| B. 严格按 `iosVisible` | iOS 端一律不展示任何领取/购买按钮，只留兑换码入口；P1 期间 iOS 用户需找客服要码 |

### 决定
**采用 A（产品负责人裁决）。**

**判定规则（端上唯一实现处：`pages/entitlement/entitlement.vue` 的 `canClaim`）**

```
price === 0                        → 可领取（与平台无关）
price > 0 且 iosVisible = true     → 可领取
price > 0 且 iosVisible = false    → iOS 隐藏按钮，改展示兑换码引导（§4：iOS 用户可见锁定态与内容清单）
```

**关键约束**：
- 判定**只读服务端下发的 `price` / `iosVisible`**，端上不写死任何价格或平台白名单。
- P1 期间「领取」不调起 `wx.requestPayment`（`settled = true` 直接刷新权益），故整条链路无支付动作。
- P2 恢复定价时**零改代码**：把商品的价格与 `ios_visible` 在后台配置好，`price > 0` 的分支自然生效。
- 非 iOS（Android / 开发者工具）不受 `iosVisible` 影响（该开关按 §4 只针对 iOS）。

## 三、决策 2：端上权益承载为**单页「我的权益」**

### 选项
| 选项 | 说明 |
|---|---|
| A. **单页「我的权益」** | 一页承载：权益概览 + 可领取内容 + 兑换码核销 + 恢复购买 + 我的订单 |
| B. 拆两页 | 「定价页」（商品 + 领取）与「我的权益页」（权益 + 订单 + 兑换码 + 恢复购买）分开 |

### 决定
**采用 A（产品负责人裁决）。**

**页面结构（自上而下）**

| 区块 | 数据来源 | 说明 |
|---|---|---|
| 权益概览 | `GET /v1/entitlements` | 双人对比报告 / 议题全包 / 已解锁议题数（`topics.length`） |
| 已解锁记录 | 同上 `items` | 逐条显示 `productCode` 对应的**商品名** + 来源（购买 / 兑换码 / 客服发放）+ 时间；商品名经「在售商品列表」映射，商品已下架时回退为「已解锁的内容」，不向用户暴露裸编码 |
| 可领取内容 | `GET /v1/products` | 每行：商品名 + 价格（P1 恒 ¥0，端上不写死）+ 权益说明（按 `benefits[].type` 给一句固定说明）+ 「免费领取」或「已解锁」或兑换码引导 |
| 兑换码 | `POST /v1/coupons/redeem` | iOS 过渡路径（§4 / E8）；失败按 60008 / 60009 / 60010 给「核对后重试 / 联系客服 / 换新码」的可操作文案 |
| 恢复购买 | `POST /v1/orders/restore-purchase` | E1 漏单兜底；`free` / `mock` 网关 `supportsQuery = false`，只返回本地状态，绝不伪造「已支付」 |
| 我的订单 | `GET /v1/orders/mine` | 商品名 + 金额 + 状态 + 时间，作为「我解锁了什么」的凭据（E3 关闭态也照实展示） |

**关键约束**：
- **解锁态只读服务端**（§14.0 不变式 1）：每次 `onShow` 重新拉取，不用本地缓存判定。
- 领取（下单）请求体**只传 `productCode`**，不传金额（E4）；`settled = true` 即刷新权益，`settled = false` 不静默失败，提示支付未开通。
- 入口只在首页与议题详情页（未到账时）出现，**不在报告页加解锁入口**：D-1 已定「被邀请方仅得 L2 基础版、L1 完整版永远只归发起方（不含任何解锁路径）」。

## 五、后果与风险

| 风险 | 缓解 |
|---|---|
| P1 豁免让 iOS 隐藏逻辑长期不被真机验证 | 判定是纯函数（`price` / `iosVisible` → 是否展示），P2 配置出 `price > 0` 后可用后台改价立即验证，无需发版 |
| 单页把 6 个区块堆在一屏，信息密度偏高 | 各区块形态统一为卡片（与首页/议题列表同构）；`我的订单` 服务端最多回 50 条，端上按接口顺序展示不额外分页 |
| 用户把「免费领取」误读为「注册即自动拥有」 | 概览区与内容区都显示当前持有状态（已解锁 / 未解锁），领取后立即刷新并以 toast 确认 |
| 兑换码入口被当作常规路径刷码 | 兑换码为一次性 + 7 天有效（E8），并发兑换由单条 `UPDATE ... WHERE status = 'unused'` 原子抢占；接口按 IP 限流 |

## 六、迁移与运维

- **无迁移**：不新增表、不新增列、不新增环境变量。
- 上线动作：小程序重新构建发版（`npm run build:mp-weixin`）；服务端无重启需求。
- P2 恢复定价时的动作清单（供未来检索）：
  1. 后台「商品管理」把 `price` 改为 8 / 3 / 19.9，并按 §4 决定 `iosVisible`；
  2. `server/.env` 把 `PAYMENT_GATEWAY` 改为 `wechat` 并填 `WXPAY_*`；重启 `zhiban-api`；
  3. 端上补一步「调起支付」：`settled = false` 时按 `launchParams.channel` 调 `wx.requestPayment`（P1 无支付动作，故本次**只保留提示与订单落库**，不写这段死代码）。
