## 一、背景

模块 1 首次编排时只把**有状态依赖**（MySQL 8 / Redis 7）写入 `docker-compose.yml`，业务 API 与 Nginx 均运行在宿主上。此后模块 2–5 的开发期部署一直沿用「宿主裸 `node dist/main.js` + `setsid nohup`」，理由只是当时阶段 3（部署收尾）尚未排期。

由此产生三处问题：

| # | 问题 | 具体表现 |
|---|---|---|
| 1 | **运维动作繁琐且易错** | 改 `.env` 后需手动「按端口找 PID → kill → `setsid nohup` 启动 → 看日志文件」；且 `ps -eo cmd \| grep dist/main.js` 会同时匹配到同机 qiyuanshe 容器内的同名进程（cwd `/app`），按名字杀进程有误杀风险 |
| 2 | **无自愈与资源约束** | 进程崩溃不自启；未设内存上限，与 qiyuanshe 同机（3.6G）存在相互挤兑风险 |
| 3 | **文档与实现漂移** | architecture.md §1 写「应用层（PM2 守护，2 实例）」，但服务器**从未安装 PM2**，实际为裸进程；同一份文件描述的应用层组件（业务 API / 管理 API / Worker）在实现上是**同一个 NestJS 进程内的模块与共享 BullMQ worker**，不是 2 个实例 |

产品负责人要求与同机 qiyuanshe 项目保持一致的运维心智：**一条命令起停**。

## 二、决策 1：服务端以单容器（`zhiban-api`）运行，纳入既有 compose 编排

### 选项
| 选项 | 说明 |
|---|---|
| A. **纳入既有 compose，新增 `api` 服务** | 与 mysql/redis 同一份 `docker-compose.yml`；`docker compose up -d` 一键起停 |
| B. 独立 compose 文件（`docker-compose.app.yml`） | 关注点分离，但需 `-f` 组合或两次命令，违背「一条命令」诉求 |
| C. 维持裸进程 + 引入 PM2 | 解决自愈但不解决环境一致性，且与 qiyuanshe 拓扑不一致 |

### 决定
**采用 A。** 新增 `server/Dockerfile`（多阶段）、`server/.dockerignore`，并在 `docker-compose.yml` 增加 `api` 服务（`image: zhiban-api:latest`、`env_file: ./server/.env`、`restart: unless-stopped`、`mem_limit: 768m`、`logging` 轮转）。

### 理由
- 与 qiyuanshe 拓扑对齐，运维命令统一为 `docker compose up -d --build` / `docker compose logs -f api` / `docker compose restart api`。
  **注意**：compose 子命令一律用**服务名** `api`；`zhiban-api` 是容器名，只适用于 `docker logs` / `docker exec` 这类原生 Docker 命令（`docker compose logs zhiban-api` 会报 `no such service`，已实测）。
- 镜像固化 Node 版本：迁移前依赖宿主 `/usr/bin/node`（v22，而 PATH 里还有 v18 软链），环境一致性靠人工保证。
- `restart: unless-stopped` + 镜像内 `HEALTHCHECK`（打 `/api/health`）提供自愈与可观测性，替代 PM2 的守护职责。

### 附带决议
- **明确放弃 PM2 方案**：architecture.md 中「PM2 守护，2 实例」随之修订为容器编排；「2 实例」在 P1 亦不落实（单实例足够，且限流/会话无跨实例共享状态需求）。
- **`.env` 不进镜像**：由 `env_file` 运行期注入，与「密钥不入库」同等级要求（`.dockerignore` 同时排除 `.env` 与 `.env.*`）。
- **日志形态变更**：由宿主 `/var/log/zhiban-server.log` 改为容器 stdout（`docker compose logs`），并配 json-file 轮转（10m × 3）。
- 种子与建号脚本改由容器内执行：`docker compose exec api node dist/scripts/seed-report-template.js` 等。

## 三、决策 2：宿主 Nginx 保留，不容器化

### 理由
- 宿主 Nginx 是**同机两个项目（zhiban / qiyuanshe）的唯一入口**，承载 `m.arvine.cn`、`zhiban.arvine.cn`、`date.arvine.cn`、`www.arvine.cn` 四个域名的 vhost。
- Let's Encrypt 证书与 `certbot-renew.timer`、`/etc/letsencrypt/renewal-hooks/deploy/*` 均挂在宿主；容器化 Nginx 需迁移证书卷并改造两个项目的回源拓扑，**改动面与排障半径显著大于收益**。
- API 容器仍以 `127.0.0.1:3000` 暴露（宿主回环），Nginx 反代配置**零改动**。

## 四、决策 3：`api` 服务使用 `network_mode: host`（安全约束，非便利选择）

### 背景
`src/common/utils/request-ip.util.ts` 中 `TRUSTED_PROXY_ADDRESSES` 硬编码为回环地址集合（`127.0.0.1` / `::1` / `::ffff:127.0.0.1`），**仅当直连方是回环地址时**才采信 `X-Forwarded-For` 并取最后一段。这是 ADR-003 后修复「伪造 XFF 绕过 IP 限流 / 绕过后台 IP 白名单」漏洞的核心机制。

### 选项
| 选项 | 后果 |
|---|---|
| A. **`network_mode: host`** | 容器内看到的直连方仍是 `127.0.0.1`（Nginx 同机回源），XFF 信任链**零改动**；`DB_HOST`/`REDIS_HOST`/`APP_HOST` 沿用 `127.0.0.1`（mysql/redis 端口已发布到宿主回环） |
| B. 桥接网络 + `ports: 127.0.0.1:3000:3000` | 容器内直连方变为 Docker 网关 IP（如 `172.x.0.1`）→ XFF **被整段丢弃** → 全体用户按网关 IP 计入同一个限流桶（大面积误伤），后台 IP 白名单判定同时失真；修复需改代码或新增可配置可信代理列表，并回归验证限流 |

### 决定
**采用 A。** 并在 compose 中以内联注释固化该约束，防止后人「顺手改成桥接网络」。

### 代价与边界
- 放弃容器网络隔离：容器与宿主共享网络命名空间。**实际暴露面无变化** —— 应用仍按 `APP_HOST=127.0.0.1` 只监听回环，公网不可直连（迁移前即如此）。
- 该方案为 Linux 专属（`network_mode: host`），与当前 CentOS Stream 9 单机部署一致；不做跨平台承诺。
- **若未来确需切桥接网络**，必须：① 把 Docker 网关网段加入可信代理列表（并保持「取最后一段」语义）；② 重跑限流回归（正常 70 次应为 60 过 / 10 个 429；每次伪造不同 XFF 结果必须一致）；③ 验证 `zhiban:rl:*` 键中解析出的是真实公网 IP 而非网关 IP。

## 五、决策 4：容器时区显式设为 `Asia/Shanghai`（并安装 tzdata）

报告标题与 L3 分享长图的日期使用**本地时区**取值（`double-report-render.service.ts` 的 `formatDate` 调用 `getFullYear/getMonth/getDate`）。基础镜像为 alpine（musl），默认无时区数据库且容器 TZ 为 UTC，若不处理，**凌晨 00:00–08:00（CST）生成的报告日期会回退一天**。

故 Dockerfile 中：`apk add --no-cache tzdata` + `ENV TZ=Asia/Shanghai`。

## 七、部署与回滚

**部署（服务器）**

```bash
cd /opt/zhiban
git pull
docker compose build api            # 首次或代码更新后
# 停掉旧的裸进程（按端口找 PID，勿按进程名杀：会误匹配 qiyuanshe 容器内同名进程）
ss -ltnp | grep ":3000"             # 取 PID
kill <PID>
docker compose up -d api            # 起容器（含 mysql/redis 依赖等待）
docker compose logs -f api             # 观察启动日志（compose 用服务名 api）
```

**日常运维**

```bash
docker compose up -d                # 起停全部（mysql/redis/api）
docker compose restart api          # 仅重启 API（改 .env 后应改用 up -d 重建）
docker compose exec api node dist/scripts/seed-report-template.js   # 跑种子
```

**回滚**（保留裸进程方案作为退路）

```bash
docker compose stop api && docker compose rm -f api
# 宿主 dist 已于 2026-09-19 清理（宿主机不再保留构建产物，镜像内 dist 才是运行版本）→ 回滚前必须先构建
cd /opt/zhiban/server && PATH=/usr/bin:$PATH npm run build
cd /opt/zhiban/server && (PATH=/usr/bin:$PATH setsid nohup node dist/main.js >> /var/log/zhiban-server.log 2>&1 < /dev/null &)
```

> ⚠️ 宿主 `server/dist` 属**旧产物**（停留在模块 2–8 期间，不含模块 6/7 的 payment / topic 控制器），
> 已于 2026-09-19 删除；此前直接在宿主 `node dist/main.js` 会静默跑起缺模块的旧版本（表现为新接口 404、启动日志里没有对应 `Mapped` 行）。
> 日常部署与临时演练实例一律走**容器内** `dist`：`docker compose build api`（`.dockerignore` 已排除宿主 `dist`，镜像内为全新构建）、
> 临时实例用 `docker compose exec -d api ... node dist/main.js`。

**验收基线**（迁移前后必须一致）

- `https://m.arvine.cn/api/health` = 200、`/api/health/ready` = 200（mysql/redis up）
- `https://zhiban.arvine.cn/` 白名单内 200、白名单外 403
- 启动日志出现 `Mapped {/api/admin/auth/login, POST} (version: Neutral) route`（后台路由回归自检点）
- 限流仍按真实客户端 IP 分桶：`zhiban:rl:POST:/api/v1/auth/login:ip:<真实公网IP>` 存在
- `https://date.arvine.cn` / `https://www.arvine.cn`（qiyuanshe）无回归

**迁移实测（2026-09-19，全部符合）**

- `zhiban-api` 容器 `Up (healthy)`，`ss -ltnp` 显示仅监听 `127.0.0.1:3000`（公网仍不可直连）
- `m.arvine.cn/api/health` = 200、`/api/health/ready` = `{database: up, redis: up}`
- 限流键实测为 `zhiban:rl:POST:/api/v1/auth/login:ip:120.208.34.16`（**真实客户端 IP**，非 `127.0.0.1` / 非 Docker 网关）→ host 网络模式的 XFF 信任链达成预期
- `zhiban.arvine.cn/` = 200、`/api/admin/auth/profile` = 401（20001，路由非 404）
- `date.arvine.cn` = 200、`www.arvine.cn` = 200、`http://date.arvine.cn` = 301
- 容器内 `new Date()` = `GMT+0800 (China Standard Time)`；镜像内无 `.env`（`env_file` 运行期注入）
- `docker compose restart api` 后 `(healthy)`、health = 200；宿主 available 约 1.3G，`zhiban-api` 常驻约 74MB
- 无 systemd/cron/rc.local 会拉起旧裸进程（`docker` 服务 `enabled`，重启机器由容器自理；若 mysql/redis 起来前 API 先启动，`restart: unless-stopped` 会在依赖就绪后自愈）
