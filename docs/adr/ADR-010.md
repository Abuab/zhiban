## 一、背景

UI 与流程重构任务要求吸收参考品的「**安全内容独立成页**」模式，并把「私密安全检查页」纳入本次重构的 9 个页面之一。

我方规格**没有任何安全类页面**：与「安全」相关的内容目前散落在三处 ——

| 现状位置 | 内容 | 问题 |
|---|---|---|
| 答题页 · 敏感维度前置同意弹窗 | B7 单独同意（`INVITE_CONSENT_TEXT` 同类文案） | 是**阻断式合规动作**，不能承载长文案 |
| 报告页 · 底线题提示 | 第 418 行中性提示「建议在关系进入下一步前充分核实与确认」 | 只说「建议核实」，**没有任何后续动作**，用户读完即走 |
| 隐私政策页 · 第七章「你的权利」 | 撤回同意 / 注销账号 | 用户要在界面上找到这些入口，必须先读完一份政策 |

由此产生三个缺口：① 底线题触发后缺少产品化的「下一步」；② 数据控制权只写在政策里，界面上找不到；③ 答题页一塞长文案就打断作答。

本页属**规格外新增功能**，按 prompt.md 铁律 #4 先写 ADR。

## 二、决策 1：新增独立页「隐私与安全检查」（`pages/safety/safety`）

### 选项
| 选项 | 说明 |
|---|---|
| A. **独立页 + 可分区块承载** | 一页承载「数据说明 / 自查清单 / 求助引导 / 数据控制入口」 |
| B. 不建页，把内容拆进答题页与报告页 | 答题页被打断，且数据控制权仍无固定入口 |
| C. 建页但只做静态说明 | 底线题触发后仍无「下一步」，等于把政策搬了个位置 |

### 决定
**采用 A。** 页面自上而下 4 个区块：

| 区块 | 内容 | 数据来源 |
|---|---|---|
| ① 我们对你的数据做了什么 | 4 条事实陈述（最小化收集 / 仅双方可见 / 中国境内加密存储 / 可随时删除） | 静态文案，与《隐私政策》第一、四、六章同源，不得出现比政策更强的承诺 |
| ② 婚前事实确认清单（可勾选） | 与底线题同方向的确认事项（婚史 / 负债 / 成瘾史 / 征信 / 体检 / 重大病史 / 彩礼房产是否已达成明确共识 / 是否互留紧急联系人） | `sys_config` 的 `safety.selfcheck.items`（json），见决策 3 |
| ③ 如果你需要帮助 | 客服二维码（后台可上传可配）+ 引导至小程序内客服入口；**未核实来源前不列任何外部渠道** | `sys_config` 的 `support.qrcode_url` / `support.qrcode_tip`，见决策 5 |
| ④ 你的数据你能控制 | 三个入口：撤回隐私同意 / 删除本次配对数据（ADR-011）/ 注销账号（既有） | 跳转既有能力 |

**本页与底线题（Q72-Q76）的关系**：区块②是底线题的**产品化延伸**，题面方向一致但**不是同一份题目** —— 不做 5 级量表、不计分、不上传、不落库。底线的**计分与提示**仍只由题库 Q72-Q76 决定（R5 / B9 不变）。

## 三、决策 2：页内自检勾选**不落库、不上传、不参与计分**

### 实现约束（硬性）
- **不新增表、不新增列、不新增写接口**；本页只读 `GET /api/v1/config/public` 取文案。
- 端上**不得**写 `uni.setStorage`（本地存储键仍只有既有 3 个）。
- 勾选状态只存在于页面 `data`，离开页面即丢弃；返回本页不要求恢复。

### 理由
1. **P3 数据最小化**：自查项覆盖婚史、负债、成瘾史、征信 —— 是本产品触及的**最敏感个人事实**，而实现「可勾选」的产品目的是**帮助用户自己想清楚**，我方**没有任何使用该数据的产品目的**。无使用目的却落库，即制造一个高价值泄露目标。
2. **题库口径唯一**：落库会让它事实上成为「第三份量表」，与「76 题 + 24 题」的既定口径冲突（`architecture.md` D-3 / A-1）。
3. **法律责任边界**：勾选结果若落库，会被解读为我方对其「事实确认结果」的留存与背书；不落库则本页仅是一次本机辅助工具。

### 被否决的替代方案
> 落库后生成「关系准备度摘要」——无任何规格依据，且把一个纯辅助工具变成"评分卡"，与 P7「不评判、不量化风险」直接冲突。

## 四、决策 3：区块②文案落 `sys_config`（含 `SysConfigService` 按 `value_type` 解释的补齐）

### 背景（实现缺口）
`sys_config.value_type` 列已存在（`schema.sql` L525），后台写入时已按类型校验（`admin-config.service.ts` L141-162：`json` 必须能被 `JSON.parse`），但**公开下发接口完全忽略该列** —— `SysConfigService.getPublicConfig()`（L34-50）只 `select configKey, configValue` 并把 `config_value` **原样当字符串**塞进嵌套对象。即：写进去是 JSON 的键，取出来是字符串。

### 决定
1. 区块②的清单落 `sys_config`：`config_key = safety.selfcheck.items`、`value_type = json`、`is_public = 1`、`config_group = site`、`config_value` 为字符串化 JSON 数组。
2. **补齐** `SysConfigService.getPublicConfig()`：按 `value_type` 解释 `config_value`（`string` 原样 / `number` → Number / `boolean` → `'true'|'false'` → Boolean / `json` → `JSON.parse`），解析失败时**跳过该键并告警**（fail-closed，沿用 ADR-002 决策 2 第 4 条的既有口径）。
3. 端上 `stores/app-config.ts` 已有的「单次去重加载 + 失败静默降级」机制复用，兜底值取端上常量（离线可见，不阻塞启动）。

### 理由
- P5 要求可见文案可配置；用户已两次裁决「代码里不要出现硬编码」。
- `value_type` 列与后台校验已把「按类型解释」写进设计，公开接口忽略它是**实现缺口而非设计选择**，补齐不改变任何既有键的行为（现有公开键只有 `brand.name`，`string` 类型结果不变）。

### 风险
`JSON.parse` 失败的行会被跳过 → 端上拿不到清单。缓解：后台写入时已校验 JSON 合法（管理后台是唯一写入口）；端上兜底常量保证页面不空白。

## 五、决策 4：入口策略「常驻弱入口 + 底线触发后显著化」

| 位置 | 形态 | 条件 |
|---|---|---|
| 首页 底部 | 小字文字链「隐私与安全检查」 | 常驻（无条件） |
| 单人报告页 顶部 | **高亮提示卡**（琥珀色描边 + 「一起做一次婚前事实确认」） | `baselineNotice != null`（底线题任一题答 1-2 分，规则 6） |
| 双人等待页 / 双人详情页 | 小字文字链 | 常驻 |
| 答题页 敏感维度前置同意弹窗 | **不出现任何跳转** | — |

### 关键约束
- 「显著化」**只读报告既有字段 `baselineNotice`**，不新增接口、不改响应协议、不做端上推断。
- **禁止**用本页替代 B7 的单独勾选同意：B7（隐私约束 2.4 / 第 81 行）要求「高敏感题目维度须单独勾选同意后才进入答题」，该勾选必须**就地在答题页完成**，不得改成「去安全页看说明后即可进入」。
- 本页**不参与**三层可见性判定：它是一个静态工具页，不承载任何对方数据（L1/L2/L3 的数据过滤规则不受影响）。

## 六、决策 5：客服二维码 —— 管理后台上传 + `sys_config` 存 URL

> 产品负责人裁决（2026-09-19）：「客服二维码要做成在管理后台可配置的格式」→ 选定**后台上传图片 + 存 URL**。

### 背景（实现缺口）
服务端**完全没有文件上传能力**：全仓无 `multer` / `FileInterceptor` / COS SDK 的任何引用。同时管理后台的配置页**只能编辑已存在的键** —— `AdminConfigService.update()` 对不存在的键直接 404（ADR-003 决策 6「只改不增删」），所以新键必须由 `schema.sql` 种子写入，不能靠后台自己创建。

### 决定

**1) 配置项（两个新键，均为 `is_public = 1`）**

| `config_key` | `value_type` | `config_group` | 说明 |
|---|---|---|---|
| `support.qrcode_url` | `string` | `support` | 客服二维码图片地址（须 HTTPS） |
| `support.qrcode_tip` | `string` | `support` | 二维码下方说明文案（如「长按识别添加客服」） |

- 沿用 `string` 而不新增 `url` 类型：`SysConfigValueType` 是 TS 联合类型，新增取值会牵动后台值校验与后台前端类型选择器，收益不足。**代价**是后台不校验 URL 格式 → 由端上 fail-closed 兜住（见下）。
- **端上 fail-closed**：`support.qrcode_url` 必须能被 `new URL()` 解析且协议为 `https:`，否则**视为未配置**（只显示客服按钮，不留空白图框）。
  > 落地修订（2026-09-19）：**小程序运行时没有 `URL` 全局对象**（微信未实现 DOM/Node 的 URL），直接 `new URL()` 会抛 `ReferenceError`。实现改为「严格 https 正则为主 + 存在 `URL` 时再解析复核一次」，语义不变（非 https / 不可解析一律视为未配置），但不再依赖宿主能力。

**2) 上传接口（后台专用，新增能力）**

```
POST /api/admin/uploads/image      multipart/form-data，字段名 file
→ { url: 'https://m.arvine.cn/uploads/<32 位随机 hex>.png' }
```

| 项 | 要求 |
|---|---|
| 守卫 | `@Public()` + `@UseGuards(AdminIpGuard, AdminAuthGuard)` —— 与 ADR-003 的**成对约束**一致（类级 `@Public()` 只是让全局 `AuthGuard` 跳过，缺 `AdminAuthGuard` 即 fail-open）；**不带** `@AllowTotpUnbound()`，即未绑二次验证的管理员不能上传 |
| 体积 | `limits.fileSize = 2MB` |
| 类型 | `Content-Type` 白名单 `image/png` / `image/jpeg`，**并且**读取文件头做**魔数校验**（PNG `89 50 4E 47`、JPEG `FF D8 FF`）—— 不信任 `Content-Type` 与扩展名 |
| 文件名 | 服务端生成 `<32 位随机 hex>.<png\|jpg>`，**不使用客户端文件名**（防路径穿越与覆盖） |
| 落盘 | `UPLOAD_DIR`（默认 `/app/uploads`），由 compose 绑定到宿主 `/opt/zhiban/uploads` |
| 返回 URL | 用 `APP_PUBLIC_BASE_URL`（新增 env，默认 `https://m.arvine.cn`）拼**绝对 HTTPS 地址**，避免端上再拼域名 |
| 审计 | 每次上传写 `audit_log`（`AuditAction.UPLOAD_IMAGE`） |
| 不做 | 不压缩 / 不裁剪 / 不生成多尺寸（二维码需保持原始清晰度） |

**3) 静态托管（nginx）**

`deploy/nginx/m.arvine.cn.conf` 新增：

```
location /uploads/ {
    alias /opt/zhiban/uploads/;
    autoindex off;
    add_header Cache-Control "public, max-age=86400";
}
```

- **为什么挂 `m.arvine.cn` 而不是 `zhiban.arvine.cn`**：小程序端要加载这张图，而 `zhiban.arvine.cn` 带 IP 白名单（fail-closed 403），小程序取不到。
- 该路径**公开可读**：二维码本身就是公开物料，且文件名 32 位随机 hex **不可枚举**。
- 挂载点必须与决策 2 的一致：**只读静态目录**，不放任何可执行内容。

**4) 运维前置条件（非代码，需你执行）**

微信公众平台 → 开发管理 → 服务器域名 → **downloadFile 合法域名** 增加 `https://m.arvine.cn`。
否则 `<image src="https://m.arvine.cn/uploads/…">` 在小程序内**加载不出来**（微信对网络图片按 downloadFile 域名校验）。退路（改用 `uni.downloadFile` 同样受限 / 把 base64 塞进配置项）都更差，故首选加域名。

**5) 端上行为**

| 情形 | 表现 |
|---|---|
| 未配置 `support.qrcode_url` | 只显示「联系在线客服」按钮，不显示空白图框 |
| URL 非法（非 https / 解析失败） | 按未配置处理（fail-closed） |
| 图片加载失败（`<image @error>`） | 隐藏图片、保留客服按钮，**不显示破图** |
| `support.qrcode_tip` 缺失 | 不显示说明文案，不显示占位空格 |

**6) 管理后台（Vue3 + Element Plus）**

- 配置页对**键名以 `_url` 结尾且 `value_type = 'string'`** 的项，额外渲染 `el-upload`（当前仅 `support.qrcode_url` 命中）；其余项保持纯输入框。
- 上传成功后把返回的 `url` **填进输入框，仍需点「保存」**才落库（避免误传即生效、也保留「改动必须留审计」的既有约束）。
- 直接粘贴外链 URL 同样允许（上传只是更省事的一条路）。

### 安全自查（铁律 #6：恶意用户会怎么攻击这里）

| 攻击 | 防御 |
|---|---|
| 上传 webshell / 伪装成图片的脚本 | Content-Type 白名单 **+** 魔数校验双保险；文件名服务端生成；目录仅静态只读 |
| 路径穿越（`../../etc/passwd` 作文件名） | 客户端文件名**完全不参与**落盘路径 |
| 超大文件耗尽磁盘 | `limits.fileSize = 2MB`；超限即拒并写 audit_log |
| 白名单外 IP 调用上传 | `AdminIpGuard` fail-closed 403（同后台其余接口） |
| 未绑 TOTP 的管理员上传 | `AdminAuthGuard` 不带 `@AllowTotpUnbound()` |
| 枚举已上传文件 | 文件名 32 位随机 hex（128 位熵） |
| 上传内容被端上当 HTML/脚本执行 | 端上只经 `<image>` 渲染；nginx 只回图片字节，不按内容协商成可执行类型 |

### 变更文件清单（本决策追加）

| 文件 | 说明 |

## 七、区块③的合规约束（重要）

- 区块③是**求助引导**，不是危机干预：不得暗示本产品提供心理诊断、心理咨询或婚姻法律建议。
- **不得编造**心理援助热线、公益组织等外部渠道。P1 只保留「小程序内客服入口」；若后续要列外部渠道，必须由运营提供**可核验的官方来源**后再独立提交变更。
- 全文适用 P7 禁词红线（第 195 行）：不得出现「不合适 / 不匹配 / 危险信号（关系判断）/ 劝分 / 重新考虑这段感情 / 离婚风险 X%」等表述；本页**不对「你的关系是否安全」下任何结论**，自查清单只陈述「可确认的事实事项」。

## 九、后果与风险

| 风险 | 缓解 |
|---|---|
| 用户误以为勾选清单会被保存 / 会被对方看到 | 区块②顶部固定一句「本清单只在本页使用，不会保存，也不会分享给任何人」；离开页面即清空 |
| 自查清单被理解为「官方婚前事实核实工具」 | 页脚沿用统一免责声明（自评量表、不构成法律/心理建议）；区块③明确本产品不提供法律意见 |
| 补齐 `value_type` 解释后，历史 `config_value` 被解析出非预期类型 | 现有公开键仅 `brand.name`（string → 行为不变）；单测覆盖四种类型 + 非法 JSON 跳过 |
| 底线触发后高亮卡片让用户误读为「你们出问题了」 | 卡片文案与报告页 `baselineNotice` 同口径（「你们对婚前事实确认的重视程度不同」），不出现判词；仅出现在**本人的单人报告页** |
| 本页成为「绕过 B7 同意」的路径 | 已在决策 4 硬性禁止；B7 弹窗内不放任何跳转链接 |
| 上传能力被误用为通用图床 | 接口只在管理后台 IP 白名单 + 管理员鉴权下可用；无「文件列表」接口；落盘名不可枚举 |
