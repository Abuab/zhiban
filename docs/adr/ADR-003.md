## 一、背景

模块 8 要求交付管理后台，规格给定的硬约束是：

> 管理后台：独立路径 + IP 白名单 + 账号密码 + 二次验证；后台接口与小程序接口分离鉴权
> —— docs/constitution.md 第 728 行

`docs/architecture.md` §6 进一步给出实现形态：「小程序 `/api/**` 与后台 `/admin/api/**` 分离；后台 JWT 独立签发 + TOTP；Nginx `allow/deny`」。

但以下 4 处规格未定义，无法直接开工，故按铁律 #2（规格没写清 → 列选项让用户选）提交产品负责人裁决：

1. 后端已有全局前缀 `/api` + URI 版本化（业务接口为 `/api/v1/**`），而架构文档写的是 `/admin/api/**`，两者的映射方式未定义；
2. 后台前端（Vue3 + Element Plus）的构建产物部署形态未定义；
3. `admin_user` 的账号来源（谁创建第一个管理员）与 TOTP 绑定流程未定义；
4. 站点配置页能否新增/删除配置键未定义。

## 二、决策 1：后台接口路径 = `/api/admin/**`（不做 rewrite）

### 选项
| 选项 | 说明 |
|---|---|
| A. **后端 `/api/admin/**`** | 后端控制器路径段用 `admin`，不参与 URI 版本化；Nginx 把 `zhiban.arvine.cn/api/admin/**` 直连反代到 `127.0.0.1:3000`，不做 rewrite |
| B. 对外 `/admin/api/**` | 严格贴合 architecture.md §6 字面；Nginx 需 rewrite 掉 `/admin` 前缀再反代到后端 `/api/admin/**` |

### 决定
**采用 A。**

### 理由
- 后台接口是**内部系统接口**，随前端一起发版，不存在「旧版客户端长期在线」的问题，URI 版本化对它没有收益；反而 `admin` 作为路径段能天然与 `/api/v1/**` 形成互斥前缀，鉴权守卫可以按前缀清晰分流。
- 与 `/api/v1/**` 的分离靠「前缀不同 + 守卫不同（AdminAuthGuard vs AuthGuard）+ 密钥不同」三重物理隔离，无需额外 rewrite。
- 少一层 rewrite：Nginx 排障时路径不必换算两次。

### 后果
- **修订 architecture.md §6 的表述**：`/admin/api/**` 改为 `/api/admin/**`（架构文档已同步更新）。

## 三、决策 2：后台鉴权与小程序鉴权物理隔离

### 决定
后台鉴权链**不复用**小程序的 `AuthGuard` / `SessionService`，四个维度全部独立：

| 维度 | 小程序侧 | 后台侧 |
|---|---|---|
| JWT 密钥 | `JWT_SECRET` | `ADMIN_JWT_SECRET`（独立环境变量） |
| JWT 载荷 | `{ sub, openid, sid }` | `{ sub, username, role, sid, **typ: 'admin'** }` |
| Redis 会话键前缀 | `session:` | `admin_session:` |
| 守卫 | `AuthGuard`（APP_GUARD 全局） | `AdminAuthGuard`（控制器级 `@UseGuards`） |

### 实现要点

1. **强制类型标记校验**：`AdminAuthGuard` 除验签外，必须断言 `payload.typ === 'admin'`。反之 `AuthGuard` 用 `JWT_SECRET` 验签 admin token 必然失败（密钥不同），双向都不可越权。
2. **admin 路由需显式标 `@Public()`**：全局 `APP_GUARD` 的 `AuthGuard` 会拦截所有路由，admin 路由用 `@Public()` 让它跳过，再由 `AdminAuthGuard` 独立校验。取舍说明：漏标 `@Public()` 的后果是「全局 AuthGuard 先以 20001 拒绝」，属 **fail-closed**（安全但报错码易混淆），可接受；反向风险（漏挂 `AdminAuthGuard` 导致后台接口裸奔）由**控制器级 `@UseGuards(AdminAuthGuard)` + 后台模块单测**覆盖。
3. **限流仍然生效**：`@Public()` 只跳过鉴权，全局 `RateLimitGuard` 照常按 IP 计数，后台登录接口另加收紧阈值。

## 四、决策 3：IP 白名单双层，应用层 fail-closed

### 决定
| 层 | 配置位置 | 行为 |
|---|---|---|
| Nginx（主防线） | `deploy/nginx/zhiban.arvine.cn.conf` 的 `allow` / `deny` | 非白名单来源在 403，请求不进入应用 |
| 应用层（兜底） | `ADMIN_ALLOWED_IPS`（逗号分隔） | 每次后台请求校验真实客户端 IP（复用 RateLimitGuard 的可信代理解析规则，只信任回环来源转发的 XFF） |

**fail-closed**：生产环境 `ADMIN_ALLOWED_IPS` 为空 → 后台接口**全部拒绝**并在启动时打 `error` 级日志提示；非生产环境为空 → 放行（便于本地调试）。

### 理由
- 如果「Nginx 白名单」与「应用层白名单」都走 fail-open，一旦两处都漏配，后台就完全敞开且没有任何提示；fail-closed 让「忘配」变成「立刻不可用 + 启动日志明确告知原因」，可自诊断、可快速修正。
- 应用层仍需兜底，因为 Nginx 配置不在代码仓库的发布流程内（改错/被回滚不会被 CI 发现）。

## 五、决策 4：账号来源 = CLI 脚本；首登强制绑定 TOTP

### 决定

1. **账号创建**：提供一次性 CLI 脚本（`npm run admin:create -- --username <name> [--role super|operator]`），密码经 stdin **隐藏回显**输入两次校验，`bcrypt` 哈希后入库。密码明文不落盘、不进 shell history、不入仓库、不进日志。
2. **TOTP 强制绑定**：`admin_user.totp_secret` 为 NULL 时，登录成功后仅可访问 TOTP 绑定相关接口，其余后台接口一律返回 `ADMIN_TOTP_REQUIRED`（引导前端跳绑定页）。
3. **绑定流程**：`POST /api/admin/auth/totp/setup` 生成 secret 并返回 `otpauth://` URL（前端渲染二维码）→ 管理员扫码 → `POST /api/admin/auth/totp/enable` 提交一次动态码 → 校验通过才写入 `totp_secret`。**未校验通过前不落库**，避免出现「绑了一半锁死自己」。
4. **登录需两步**：`POST /api/admin/auth/login` 提交 `username + password + totpCode`（首次登录时 `totpCode` 可省略，用于进入绑定流程）。

### 理由
- 规格要求「账号密码 + 二次验证」，TOTP 是 `architecture.md` §6 明确的落地方式。
- 账号不能走 SQL 种子：种子 SQL 要么写明文口令（违反安全基线），要么写固定哈希（等于全网已知口令）。CLI 是唯一既能自动化又不落明文的路径。
- 「绑定前只给绑定页权限」是防锁死的必要设计：管理员忘记绑定就登录不进后台，但也不会把自己彻底关在门外。

## 六、决策 5：后台前端静态托管于宿主 Nginx

### 决定
后台前端构建产物放服务器 `/opt/zhiban/admin/dist`，由宿主 Nginx 以 `root` + `try_files … /index.html` 直接托管；**不新增容器**。

### 理由
- 服务器仅 3.6G 内存，现有拓扑是「宿主 Nginx 唯一入口」（qiyuanshe 的容器已占 2.5G 限额）；
- 管理后台是 SPA，无 SSR 与动态进程需求，静态托管是最小方案（P6「够用为限」）；
- 与 `m.arvine.cn` 共用同一套 nginx 配置管理方式（仓库文件 + 软链 + `nginx -t && reload`）。

### 后果
- 后台前端与后台接口**同域**（`zhiban.arvine.cn`），无 CORS 需求。
- 部署流程：服务器 `git pull` → `cd admin && npm ci && npm run build` → 产物落在 `admin/dist`（Nginx root 直接指向它，无需拷贝）。

## 七、决策 6：站点配置页「只改不增删」

### 决定
后台站点配置页（本期范围：「系统设置 → 品牌与站点」）仅允许**编辑已有行的** `config_value` / `is_public` / `description`；**不允许新增或删除配置键**。

### 理由
- `sys_config` 的键是被代码消费的（键名决定小程序端读哪个字段）。后台新增一个没有消费方的键不会产生任何效果，只会制造「配了却没生效」的误导。
- 删除键会让线上小程序立刻丢失该配置（回退到构建期兜底值），是「自己把自己配崩」的高危操作，收益为零。
- 新增配置键的正确路径 = 改 `docs/schema.sql` 种子 + 消费方代码 + 发版（确实需要发版，因为**消费方是新代码**，这与 P5「改内容不发版」不冲突：P5 管的是内容，不是新增配置项本身）。
- 符合 P6「后台功能以够用为限，拒绝过度设计」。

### 后果
- 配置页需要分组（`config_group`）+ 分页展示，并对 `value_type` 渲染不同控件（string→输入框 / number→数字框 / boolean→开关 / json→多行文本 + JSON 合法性校验）。

## 八、依赖引入

| 依赖 | 用途 | 选型理由 |
|---|---|---|
| `bcryptjs` | 管理员口令哈希（`admin_user.password_hash` 注释要求 bcrypt） | **纯 JS 实现**，无原生编译。服务器为 CentOS Stream 9，`bcrypt` 原生模块需要 node-gyp + python + gcc 工具链，是「一人可运营」下的额外运维负担 |
| `otplib` | TOTP 动态码生成与校验（RFC 6238） | 纯 JS，无原生依赖；支持 `authenticator.keyuri()` 直接产出 `otpauth://` URL |

> 备选 `argon2`（更抗 GPU 爆破）与 `bcrypt`（原生模块）均被否，理由见上表。

## 九、总后果与风险

| 风险 | 缓解 |
|---|---|
| `@Public()` 让全局 AuthGuard 放行 admin 路由，存在「漏挂 `AdminAuthGuard` 即裸奔」的隐患 | 后台控制器一律在**类级**标注 `@UseGuards(AdminAuthGuard)`；新增后台控制器必须挂守卫，由后台模块单测覆盖「无 token 访问 → 401」 |
| `ADMIN_ALLOWED_IPS` 漏配导致生产后台全拒 | fail-closed + 启动 `error` 日志；`.env.example` 与部署说明标注必填 |
| Nginx 白名单与 `.env` 白名单不同步（如只改了一处） | 两处均以「逗号分隔 IP」为唯一格式；ADR 与部署说明要求同时修改；应用层拒绝时返回 `IP_FORBIDDEN(70002)` 便于定位是哪一层拦的 |
| TOTP secret 明文存库（`admin_user.totp_secret`） | 库仅本机 127.0.0.1 可达；登录密码本身仍是第一道防线；后续如需可引入 secret 加密（已记入风险，不在本期范围） |
| 管理员忘记密码 / 丢失 TOTP 设备 | CLI 脚本支持重置（重置后 `totp_secret` 置 NULL，回到「首登强制绑定」流程），无需数据库手工操作 |
| 后台接口被爬（虽已 IP 白名单） | 登录接口收紧限流；非白名单来源在 Nginx 层即被拒 |
