## 一、背景

模块 5（双人邀请与对比报告，prompt.md 第 92-96 行）要求：状态机、邀请码绑定首个授权人 C1、答案复用 C3、30 天过期 C4、换人 C7、三层可见性 R3、底线题双向提示 R5、复用历史快照 B8。**完成标准：两个测试账号完整走通流程；越权测试拒绝访问。**

开工前发现 **2 处产品裁决 + 3 处 schema 无位置**：

| # | 议题 | 规格要求 | 现状 |
|---|---|---|---|
| 1 | **越权返回码** | prompt.md 第 95 行要求「越权测试返回 403」；architecture.md §3.2 亦写 403 | ADR-004 决策 6 刚把越权与「不存在」统一为 `10002/404`（防 id 枚举 oracle）→ **互斥** |
| 2 | **L1 维度解读分档** | 价值感标准 §一：每维度 300-500 字 = 「分数含义 + 你们这分数常见原因 + 1 个具体情境」 | 规格只定义**差值**阈值（R1 的 15/30，后台可配），**未定义单人绝对分数**档位 → ADR-004 决策 3.5 记为阻塞待办 |
| 3 | **换人次数无处落库** | C7：被邀请方拒绝同意 → 发起方可换人重邀，**限 1 次** | `invite` 表无换人链字段；历史行保留但行间无关联，`replaced` 次数不可判定 |
| 4 | **模板分档无处表达** | 决策 2 要求同一维度按差值等级给不同文案（8 维度 × 3 档） | `report_template_block` 无档位列；`block_key` 是 `VARCHAR(32)`，用后缀编码属隐藏约定 |
| 5 | **L3 分享长图生成方未定** | D2 要求长图失败可降级；PRD-002 §7 有 `POST /reports/:id/share-image` | architecture.md §3.2 设计为「服务端生成 + 上传 COS」，但 **P1 无 COS/OSS、服务器无 canvas 库** |

## 二、决策 1：越权与「不存在」继续统一为 `10002/404`（沿用 ADR-004 决策 6）

### 选项
| 选项 | 说明 |
|---|---|
| A. **统一 `10002/404`** | 邀请/报告资源的越权访问与「不存在」返回同一错误；越权记 `audit_log` + warn 日志 |
| B. 按 prompt.md 回 `403` | 越权 `10004/403`，不存在 `10002/404` |
| C. 报告 403、答题卷 404 | 按资源类型区分 |

### 决定
**采用 A（产品负责人裁决）。** 并修订三处与本决策冲突的表述：
- `prompt.md` 第 95 行「越权测试（A 访问 B 的报告）返回 403」→ 「…返回拒绝访问（`10002`/404，与「不存在」同一响应）」
- `architecture.md` §3.2「非参与方 → 403（不返回任何存在性信息）」→ 「→ `10002`/404（与不存在的邀请同一响应，**不返回任何存在性信息**）」
- `architecture.md` §3.2 L3「校验 V = initiator（否则 403）」→ 「（否则 `10002`/404）」

### 理由
- 宪章 F4（P0）只要求「逐请求校验资源归属 + 越权尝试记日志/告警」，**未要求**对外区分两类失败；区分是实现自行引入的信息，去掉不违反任何规格。
- 可观测性由服务端承载更完整：越权照常写 `audit_log` 与 warn 日志（含 `invite_id` / 访问者 `uid`），用户侧看不到差异。
- 双人报告涉及双方数据（隐私约束 2.4），枚举 oracle 的后果比单人测评更重：能判断「哪些 invite 真实存在」。虽然 C8 已用 128 位随机邀请码让**码**不可枚举，但**自增 id** 仍可被探测，故必须堵。
- 客户端无感：端上对两类失败本就同处理（提示并返回首页）。

## 三、决策 2：L1 维度解读**按差值等级**分档，零新增阈值

### 选项
| 选项 | 说明 |
|---|---|
| A. **按差值等级分档** | 复用 R1 已有的 15/30（后台可配、D6 边界归低一级），无需发明新阈值 |
| B. 按双方得分均值的四分档 25/50/75 | 与 5 点量表语义对齐（均分 2/3/4 → 25/50/75），但需新增一套阈值 |
| C. 按双方得分均值三分档 33/67 | 同上，需新增阈值 |
| D. 不分档 | 每维度一段固定文案 |

### 决定
**采用 A（产品负责人裁决）。**

### 理由
- 对比报告的核心度量就是**差值**，规格原文「你们这分数」在双人语境下即差值；而差值阈值 R1 已定义且**后台可配**，属「规格已写清」的范畴 → 不发明新阈值，不触碰铁律 #1。
- 分档依据与「待沟通区」同源（同一份 `dimension_scores_json` + 同一组阈值），不会出现「维度解读说高共识、待沟通区却列了它」的口径矛盾。
- **ADR-004 决策 3.5 的阻塞待办随之消解**：单人简版仍按 ADR-004「不做分档」（规格未定义单人绝对分数档位），双人完整版按差值分档（规格已定义）。

### 实现要点
- `report_template_block` 增 `gap_level VARCHAR(8) DEFAULT NULL`（`high` / `mid` / `low`；`NULL` = 不限档，用于 INTRO / 共识区 / 结尾等非分档区块）。
- 渲染时按「该维度在 `diffs_json` 中的 `level`」选取对应档位的 block；同 `block_key` 只渲染命中档位的那一条。
- **显式列而非 `block_key` 后缀编码**：`FINANCE__high` 这类编码是隐藏约定（不可枚举、不可查询、后台无法按档位筛选），而模块 8 的「报告模板」页需要按档位编辑。

## 四、决策 3：`invite` 增 `replaced_from_invite_id`（C7 换人限 1 次可判定）

### 选项
| 选项 | 说明 |
|---|---|
| A. **增 `replaced_from_invite_id`** | 新邀请指向被拒绝的那条邀请；「同一 declined 邀请最多派生 1 条」即 C7 的「限 1 次换人」 |
| B. 增 `replacement_count`（发起方维度计数） | 按发起方累计换人次数 |
| C. 不增列，仅按 `status=declined` 的历史条数限制 | 无需 schema 变更，但无法区分「一个邀请被换人」与「多个邀请各自被拒」 |

### 决定
**采用 A。** 新增列 `replaced_from_invite_id BIGINT UNSIGNED DEFAULT NULL` + `KEY idx_replaced_from (replaced_from_invite_id)`。

### 理由
- C7 原文「被邀请方拒绝同意 → 发起方可换人重邀 **1 次**」的计数单位是**一次邀请事件**，不是发起方累计次数 → A 与规格同粒度；B 会误伤「换人对象也无故拒绝」之外的正常场景（如另一次独立邀请被拒）。
- C 无法判定：历史行保留但 `declined` 行既可能来自「被拒后换人」，也可能来自「发起方放弃」，把两者都算作已用换人名额会误伤。
- 保留历史行（架构 §8 C7）不变：旧邀请行原样留档，新邀请用该列指回旧行，链路可审计。

## 五、决策 4：报告生成走 Redis + BullMQ（沿用架构 A-6）；**L3 长图改由小程序端 canvas 生成**

### 5.1 报告生成：Redis + BullMQ（无争议，照架构执行）
- 队列 `report:generate`，job payload `{ inviteId }`；在**被邀请方交卷后双方齐备**时入队（R6）。
- 失败自动重试 **3 次**（D1）；末次失败置 `report.status='failed'` 并写 `job_task` 转人工工单（D1）。
- 幂等：同一 `invite_id` 的 job 用 `jobId = report:<inviteId>` 去重；worker 内先查 `report` 是否已 `ready`。
- 前端轮询 `GET /invites/:code/report` 拿 `status`（R6）。
- 过期扫描用 BullMQ **repeatable job**（每小时），不引入 `@nestjs/schedule`。

### 5.2 L3 分享版长图：小程序端 canvas 生成（产品负责人裁决）
| 选项 | 说明 |
|---|---|
| A. **小程序端 canvas 生成** | 服务端下发「可勾选区块 + 水印串 + 已过 P7 过滤的文案」，端上合成并保存/分享 |
| B. 服务端 node-canvas | 服务器需装 cairo/pango 编译链，产物写本地由 Nginx 托管 |
| C. P1 不做长图 | 仅微信好友分享卡片 |

### 决定
**采用 A。**

### 理由
- B 的代价与收益严重失衡：P1 无对象存储（架构 §1 长图本应走 COS+CDN），把原生编译链装进生产服务器是为一个非核心功能引入长期运维负担。
- A 天然满足 D2（长图生成失败 → 降级为普通分享卡片）：端上绘制失败即回退微信好友卡片，服务端无失败面。
- 水印溯源（D3：右下角嵌 user_id 哈希）由服务端下发**哈希串**、端上绘制，哈希在服务端计算 → 水印值不可被前端伪造。
- **端点保持 PRD-002 §7 的路径**：`POST /reports/:id/share-image` 语义由「返回图片」变为「下发长图素材」（`blocks[]` + `watermark` + `title` + `nicknames` + `date`），端点名与调用方不变。

### 实现要点
- 服务端在返回素材前执行 **P7 禁词过滤 + 白名单裁剪**（架构 §3.2：L3 不出现分数、不含差值/分歧），并写 `visibility_log(level='L3', action='share_image_created')`。
- 端上 `canvas 2d` 绘制「纪念证书」（囍印/边框/双方昵称/日期）+ 右下角 subtle 水印。

## 六、决策 5：L2/L3 模板不做逐报告版本冻结，仅 L1 记录 `template_version_id`

### 背景
`report.template_version_id` 是**单值**列，而双人报告有 L1/L2/L3 **三套**模板；D5 要求「历史报告用其生成时的模板版本渲染」。

### 决定
- `report.template_version_id` 存 **L1 模板 id**（权威模板，含全部维度解读与逐题分歧）。
- L2/L3 模板按 `(audience='double', scale_version_id, level, status='on')` **取 id 最大者**解析，不逐报告冻结。

### 理由
- L1 是付费/核心产物，其文案随分值档位变化最需要版本冻结；L2/L3 只承载通用文案 + 共识区原文（数据来自 `report.consensus_json`），运营改文案即时生效是可接受的。
- 若为 L2/L3 也做冻结，需增 JSON 映射列或每报告插 3 行关联，收益不抵复杂度（违反「避免过度设计」）。
- 风险已在下方风险表登记；若 P2 恢复付费、L2/L3 成为独立付费点，应重新评估。

## 七、决策 6：提醒（订阅消息）未配置模板或发送失败时**不消耗** `remind_count`

### 决定
- 前置：`remind_count < 3`（PRD-002 §5）。
- 发送成功（微信返回 `errcode=0`）才 `remind_count += 1` 并更新 `remind_at`。
- 模板未配置（`WX_SUBSCRIBE_TEMPLATE_INVITE` 为空）或发送失败 → 返回明确业务错误 + 日志，**不消耗次数**。

### 理由
- 次数是给用户的**稀缺额度**（限 3 次）；消耗了却未送达，等于骗走用户额度，属「涉及权益的代码」自查项。
- P1 阶段订阅模板可能尚未在微信后台建好，若按「发送即计数」实现，联调期会把 3 次额度耗尽且现象难排查。

## 八、决策 7：P1 免费下的创建邀请前置条件与状态机保留

### 决定
- `invite.amount = 0.00`，创建邀请**无支付节点**；状态机仍保留 `invite_created` 作为首态（不新增 `created` 状态），以便 P2 恢复付费时无需改动状态迁移表。
- 创建前置（架构 §3.1 步骤 1-5 原文）：① 发起方**已完成本人单人测评**（存在已交卷的 `scene='single'` 答卷）② 发起方**无进行中邀请**。
- **「进行中」定义**：`status IN ('invite_created','invite_opened','consent_given','answering','completed')`。终态（`report_unlocked` / `expired` / `declined` / `cancelled`）不占用额度 → 历史报告永久可回看（PRD §5）。
- 对齐说明：边界总表 C5（P0）「不限制同时邀请第二个人」与 PRD-002 §5「同一发起方同时最多 1 个进行中邀请」字面冲突，按**优先级规则（PRD > 边界总表）**取后者（产品负责人裁决）。C5 的合理内核（历史/已完成邀请不设上限、报告按 invite 粒度隔离）已被上述「进行中」定义完整保留。

### 附带约束
- 复用答案（C3/R7）：被邀请方须**已完成同 `scale_version_id`** 的单人测评才可复用；复用需本人显式确认；写入 `answer_snapshot.is_reuse=1` 且直接进入 `completed`。版本不一致时**不允许复用**（B8 快照一致性）。
- 状态机接口的局部更新一律用 **`PUT`**（微信 `wx.request` 的 method 合法值不含 `PATCH`，沿用 ADR-004 决策 4）。architecture.md §3.1 步骤「PATCH /invites/:code/answers」同步改为 `PUT`。
- 敏感维度跳过（B7）在双人流程中同样适用；被跳过维度**不参与差值比对**（无分数）→ 该维度不进入待沟通区，报告统一标注「未评估」。

## 九、总后果与风险

| 风险 | 缓解 |
|---|---|
| 两处 schema 变更需在生产 `ALTER TABLE` | 均为**纯增列且可空**（`invite.replaced_from_invite_id`、`report_template_block.gap_level`）+ 1 个新增普通索引；对存量 0 行表零风险；执行前 `mysqldump` 备份 |
| 引入 BullMQ 新依赖（`bullmq` + `@nestjs/bullmq`） | 架构 A-6 已裁定；复用现有 Redis 实例（同库不同 key 前缀隔离），不新增服务 |
| worker 失败导致报告长期 `pending` | D1 重试 3 次 + 末次失败置 `failed` 并写 `job_task`；前端 `status` 轮询可显示「生成中/失败」 |
| L2/L3 模板不冻结版本，改文案影响历史报告 | 已登记；L2/L3 不含差值与分歧数据，影响面为通用文案；P2 若成为独立付费点需重新评估 |
| 小程序端 canvas 生成长图失败 | 即降级为微信好友分享卡片（D2 的预期行为，非异常） |
| 水印值被前端伪造 | 水印哈希由服务端计算后下发（端上只负责绘制），且不参与任何权限判定（仅溯源） |
| 「进行中」定义过严影响 P1 体验 | 与 PRD-002 §5 一致；若产品实测觉得受限，放宽只需改一个 `status IN (...)` 常量 |
